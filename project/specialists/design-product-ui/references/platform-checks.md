## 共同原则

- 保持任务语义、信息层级、品牌角色和状态语言一致。
- 允许导航、窗口、输入、控件形态和系统反馈按平台适配。
- 以项目实际支持版本为边界，不默认使用最新 API。
- 用真实设备或平台模拟器验证关键流程；截图不能验证触摸、焦点、键盘和系统返回行为。
- 将平台差异写成明确决策或组件映射；未确认提案列为 `proposed`；既有批准、用户选择与授权代理决策分别注明来源，记录到现有设计规范。

## Web 与 Web 壳客户端

适用于浏览器、Electron、Tauri WebView 和其他 HTML/CSS 界面：

- 定义内容宽度、断点行为、容器查询或流式布局策略。
- 保持语义 HTML、可见焦点、合理 tab 顺序和跳转/深链能力。
- 确保 URL、历史返回和刷新能恢复有意义的导航或筛选状态。
- 为鼠标、键盘、触摸和触控板提供等价路径；不要依赖 hover 才能发现核心能力。
- 处理浏览器缩放、字体放大、窄屏、超宽屏和 reduced motion。
- 验证图片尺寸、字体加载、布局偏移、长列表和动画性能。
- Electron/Tauri 还需验证窗口最小尺寸、原生菜单、拖拽区、文件选择和系统快捷键。

## iOS 与 macOS

- 尊重 safe area、Dynamic Type、VoiceOver、系统返回/关闭语义和平台控件预期。
- iOS 优先考虑单手触达、手势返回、键盘遮挡、权限说明和中断恢复。
- macOS 明确窗口缩放、菜单栏、工具栏、侧栏、键盘快捷键、焦点环和多窗口行为。
- 不照搬 Web 导航、hover 或弹窗模式；使用项目已经采用的 SwiftUI/UIKit/AppKit 体系。
- 使用系统材质、动画或新视觉 API 前确认最低系统版本与降级路径。

## Android

- 处理系统返回、edge-to-edge、状态/导航栏、键盘、旋转和窗口尺寸类别。
- 让导航结构匹配手机、折叠屏、平板和桌面窗口，而不是只放大手机布局。
- 支持 TalkBack、字体缩放、触摸目标和系统 reduced-motion/动画设置。
- Material 组件和品牌语言冲突时，优先保持交互语义和可访问性，再定制视觉 token。
- 确认项目实际使用 View、Compose 或混合架构，并按其组件与状态模型实现。

## React Native 与 Flutter

- 共享信息架构和业务语义，保留 iOS/Android 导航、返回、菜单、日期选择和权限差异。
- 使用 safe area、键盘避让、字体缩放和可访问性 API，不用固定像素复制设计稿。
- 明确哪些组件是共享视觉语言，哪些应由平台条件渲染。
- 在至少一个小屏和一个大屏设备上验证；需要平板/桌面支持时增加相应窗口类别。
- 检查列表、图片、动画和导航性能，避免为了视觉一致性牺牲原生反馈。

## 桌面客户端

适用于 Qt/QML、JavaFX、WPF/WinUI/Avalonia、Rust egui/iced 等：

- 先定义窗口最小/默认/最大布局行为、面板缩放和高 DPI 策略。
- 支持键盘导航、快捷键、焦点、右键菜单、拖放、窗口恢复和多显示器。
- 区分鼠标密集型工具与触屏桌面；信息密度和目标尺寸不应使用同一默认值。
- 对工具型界面明确选择、编辑、保存、撤销、脏状态和关闭保护。
- Qt/QML 项目在宿主已提供时优先使用 Qt 官方 `qt-ui-design`；否则依据项目现有 QML 与 Qt 平台约束实施。本 skill 只维护项目体验与视觉语言。
- JavaFX、WPF 或 Rust UI 应记录控件主题、token 映射和平台差异，避免每个页面直接写颜色和尺寸。

## 嵌入式与大屏

- 记录观看距离、分辨率、亮度、输入设备、响应延迟和安全等级。
- 使用强层级、较大文字和目标，减少精细手势和隐藏交互。
- 对遥控器、旋钮、方向键或硬件按键定义焦点顺序和可见反馈。
- 危险动作必须防误触，并能在网络中断、设备忙或部分失败时恢复。
- 监控大屏区分环境态势与可操作控件，避免用颜色作为唯一告警等级。

## 跨平台一致性

建立组件或模式映射表：

| 产品语义 | Web | iOS/macOS | Android | 其他客户端 | 不变量 |
| --- | --- | --- | --- | --- | --- |
| `<主要动作>` | `<组件>` | `<组件>` | `<组件>` | `<组件>` | `<结果与文案>` |
| `<返回/关闭>` | `<行为>` | `<行为>` | `<行为>` | `<行为>` | `<是否保存/确认>` |
| `<错误恢复>` | `<模式>` | `<模式>` | `<模式>` | `<模式>` | `<错误语义>` |

当平台习惯冲突时依次判断：

1. 项目已有设计系统是否已解决。
2. 是否能在运行时使用平台原生行为。
3. 若必须统一，哪个方案最少增加误解、错误和可访问性风险。
4. 将用户选择或授权范围内的代理决策、放弃方案和平台 QA 要求写入现有设计规范，分别注明决策来源。
