# Design Product UI

把设计当作项目约束和产品决策，而不是一次性的视觉装饰。先理解用户任务与现有系统，再决定是否需要新方向；将获批的稳定决策写入项目 `DESIGN.md`，把实现、交互状态和视觉验证交给当前宿主可用的工具完成。

## 保持边界

- 不接管通用计划、代码编辑、测试、构建或 Git 流程。
- 不把没有证据的竞品印象、用户研究或可访问性结论写成事实。
- 不因启用本 skill 就重塑已有品牌；现有 tokens、组件、产品语义和已确认设计优先。
- 不封装特定浏览器、图片生成器或框架。使用宿主已有的设计、图片、浏览器和设备工具；不可用时明确降级。
- 不把风格清单当设计答案。任何颜色、字体、布局或动效都必须服务于当前产品、用户任务和平台。

## 选择工作深度

先分类，再决定流程深度：

| 类型 | 典型任务 | 必需动作 |
| --- | --- | --- |
| 局部调整 | 一个组件、一个状态、明确的样式修正 | 读取现有系统，直接实施并做局部视觉验证；不要重写 `DESIGN.md` |
| 页面或流程 | 新页面、多状态表单、导航或关键用户路径 | 建立 brief、状态模型、布局与交互方案，再实施和验证 |
| 新方向或设计系统 | 新产品、品牌重塑、多个页面需要统一语言 | 比较方向，等待选择，建立或更新 `DESIGN.md` 后再生产实现 |
| 设计评审 | 评审现有页面、截图、流程或实现 | 只读收集证据并输出发现；除非用户要求，否则不要修复 |

## 1. 读取项目事实

按相关性读取，不做无边界扫描：

1. 项目 `AGENTS.md`、需求或用户故事。
2. 根目录 `DESIGN.md`、设计 tokens、主题、字体和图标配置。
3. 同一用户流程的现有页面、组件和真实内容。
4. 路由、状态模型、错误文案、国际化和可访问性实现。
5. 视觉回归、组件预览、截图或设备验证入口。

区分“明确设计决策”“当前实现事实”和“历史偶然结果”。文档与现有 UI 冲突且会改变产品身份或公共组件时，先暴露冲突，不要静默选择一方。

## 2. 锁定 Design Brief

在页面或更大任务中，用最短形式确认：

- 主要用户及其使用情境。
- 界面唯一的主要任务和成功结果。
- 必须呈现的信息、主要动作和恢复动作。
- 目标平台、输入方式、屏幕范围与环境约束。
- 已有品牌、组件、参考设计和不可改变项。
- 需要覆盖的 loading、empty、error、disabled、permission、offline 和 success 状态。

只询问会实质改变设计的未知项。局部调整或答案已能从项目中获得时，继续执行。

## 3. 通过 Direction Gate

根据约束选择路径：

- 已有设计稿、明确方向或成熟设计系统：忠实遵循，不额外制造方向。将“现代一些”“高级一些”等主观描述转译为可验证的原则，但不因此启动多方向探索。
- 用户明确要求探索方向，或信息架构 / 视觉语言仍开放且选择会影响多个屏幕：提出 2–3 个真正不同的候选，等待用户选择后再写生产实现。
- 只有一个方向合理：给出理由和主要风险，直接进入细化。

局部产品规则、权限或安全契约未定时，把它们列为待确认决定，不自动视为多方向探索。

只有进入多方向探索时，每个候选才需至少说明：设计 thesis、与产品语义的联系、一个 signature、颜色角色、字体角色、布局逻辑、交互/动效策略、适用风险。宿主支持视觉探索时，优先生成可比较的 mockup；不要用三段相近的形容词假装成三个方向。

创建或重塑视觉方向时读取 [craft-principles.md](references/craft-principles.md)。

## 4. 固化项目设计系统

只在决策需要跨页面、跨会话复用时维护根目录 `DESIGN.md`：

- 文件不存在时，以 [DESIGN.template.md](assets/DESIGN.template.md) 为起点。
- 文件存在时，局部更新已确认的章节；保留仍有效的项目决定和决策记录。
- 记录语义 token 和组件角色，不把零散十六进制颜色或某个页面坐标当系统。
- 将代码中的 token、主题或公共组件路径映射回文档，避免设计文档与实现各自演化。
- 对尚未确认的内容标记 `proposed`，不要伪装成既定规范。

## 5. 设计完整体验

在写视觉细节前，先完成信息与行为：

1. 排出信息优先级和一个占主导地位的下一步动作。
2. 为每个关键状态提供明确反馈和恢复路径。
3. 定义导航、返回、取消、保存、重试和危险动作语义。
4. 只为目标平台实际支持的尺寸、横竖屏、窗口和输入方式定义适配行为。
5. 使用真实或结构真实的内容检查溢出、空值、长文本和本地化。
6. 选择现有组件或提出最小的新 token / 组件扩展，避免页面级特例累积。

涉及具体平台时只读取 [platform-checks.md](references/platform-checks.md) 中对应章节。平台原生约定与统一品牌语言冲突时，保留任务语义，允许控件和导航行为按平台适配。

## 6. 实施与验证

实施时：

- 从一条代表性用户路径或页面 vertical slice 开始。
- 从设计 token 派生颜色、字体、间距、圆角、阴影和动效。
- 复用项目组件；新增公共抽象前先证明至少存在两个稳定消费者或明确的系统价值。
- 同时实现正常、加载、空、错误和禁用等已声明状态。
- 保持语义结构、键盘/焦点、触摸目标、屏幕阅读器和 reduced-motion 支持。

验证时组合两类证据：

1. 运行项目已有的测试、构建、lint、组件预览或设备检查。
2. 在代表性视口、主题、状态和输入方式下采集视觉证据，检查层级、溢出、对比、焦点、适配和交互反馈。

仅在设计评审、实现即将交付，或用户明确要求质量审查时读取 [review-rubric.md](references/review-rubric.md)；纯概念方案默认不读取。无法运行视觉或设备验证时，明确列出未验证项，不以源码检查冒充实际渲染结果。

## 停止并请求决定

仅在以下情况暂停受该决定影响的详细设计和生产实现。仍可以输出不依赖该决定的稳定流程骨架、约束和推荐默认值：

- 主要用户、主要任务或两个竞争动作会导向不同的信息架构。
- 缺失用户指定的截图、设计稿、品牌资产或必要平台环境。
- 现有设计系统与线上实现发生影响多个页面的实质冲突。
- 需要新增公共 token、组件或依赖，且明显扩大项目范围。
- 平台惯例、可访问性或安全要求无法与当前交互模型同时满足。

## 输出契约

按任务只输出必要内容：

- **方案**：brief、方向或 wireframe、状态/交互、响应式/平台策略、token/组件影响和待确认决定。
- **实施**：已确认方向、实现范围、`DESIGN.md` 变化、视觉证据、已运行验证和剩余风险。
- **评审**：按优先级列出有截图或源码证据的发现、用户影响、建议和验证方式；不要用无上下文的审美评分代替判断。
