# UI/UX Review Rubric

## 使用方法

把评审当作基于证据的风险检查，不把总分当成审美真理。

1. 明确评审对象、用户任务、平台和视口/设备范围。
2. 获取或复用实际渲染截图、设备画面；源码与 tokens 仅在可获取且结论需要时定位。
3. 逐项判断用户影响；只报告能说明证据和修复方向的问题。
4. 先报告阻断任务、误导用户和可访问性失败，再报告一致性和润色。
5. 用户只要求评审时保持只读。

## 严重度

| 等级 | 定义 | 示例 |
| --- | --- | --- |
| P0 | 阻止主要任务、造成危险或严重误导 | 无法提交、危险动作误触、关键内容不可读 |
| P1 | 明显损害理解、恢复、可访问性或主要平台适配 | 错误无恢复、键盘不可达、移动端主动作被遮挡 |
| P2 | 降低效率、一致性、信任或视觉层级 | 状态不一致、密度失衡、组件变体漂移 |
| P3 | 局部润色问题，不影响完成任务 | 轻微对齐、节奏或细节不统一 |

## 十个检查维度

### 1. 任务与信息架构

- 屏幕目的、当前状态和主要动作是否在第一次扫视中清晰？
- 内容顺序是否匹配用户决策，而不是数据结构或实现顺序？
- 次要信息是否适当延后，关键警告是否没有被隐藏？

### 2. 导航与连续性

- 进入、返回、取消、关闭、保存和恢复行为是否可预测？
- 深链、刷新、窗口恢复或系统返回是否保持有意义的状态？
- 多步骤流程是否显示进度、退出后果和重新进入方式？

### 3. 状态与恢复

- loading、empty、error、disabled、permission、offline 和 success 是否按需要覆盖？
- 错误是否具体、就近并提供下一步？
- 异步操作是否防止重复提交、陈旧状态和不明确等待？

### 4. 视觉层级

- 尺寸、位置、留白、对齐和对比是否表达真实优先级？
- 是否过度依赖卡片、边框、阴影、颜色或装饰性标签？
- signature 是否集中且服务产品，而不是每个区域都争夺注意力？

### 5. 设计系统一致性

- 是否复用项目 tokens、组件、图标和文案模式？
- 新值和新变体是否有系统角色，还是页面级例外？
- 项目现有设计规范、代码 token 和实际渲染是否发生漂移？

### 6. 响应式与平台适配

- 内容是否在目标小屏、宽屏、横竖屏和窗口缩放下重新组织？
- 是否存在截断、重叠、非预期滚动或固定高度失效？
- 导航、输入和系统行为是否符合目标平台和设备？

### 7. 可访问性

- 语义、标签、焦点顺序、可见焦点和屏幕阅读器反馈是否完整？
- 字体缩放、对比、触摸目标和颜色非唯一信号是否满足项目标准？
- reduced motion 是否可用，动画是否不是任务完成的前提？

### 8. 内容与本地化

- 文案是否从用户视角描述动作、状态和恢复？
- 真实长文本、空值、数字、日期、单位和语言扩展是否可容纳？
- 图标、颜色、格式或隐喻是否依赖未经验证的文化假设？

### 9. 动效与反馈

- 每个交互是否有及时、与因果一致的反馈？
- 动效是否解释空间或状态，而非增加等待和干扰？
- 慢设备、低帧率和禁用动画时是否仍能理解界面？

### 10. 性能与实现韧性

- 字体、图像、滤镜、长列表和动画是否符合目标设备预算？
- 组件是否能处理真实数据、失败、权限变化和并发交互？
- 视觉修正是否引入脆弱选择器、页面覆盖或不可维护的硬编码？

## 视觉验证矩阵

从项目支持范围选择最小但有代表性的组合：

| 轴 | 至少验证 |
| --- | --- |
| 尺寸 | 最小支持尺寸、主要尺寸、一个宽屏或大字号场景 |
| 主题 | 默认主题；项目支持时增加深色或高对比 |
| 状态 | 正常、加载、空、错误，以及该流程最危险的状态 |
| 输入 | 项目支持的键盘、鼠标、触摸、返回键或遥控器 |
| 内容 | 短文本、长文本、真实数据边界和本地化样本 |

## 发现格式

每个发现包含：

- `P0–P3` 严重度和简短标题。
- 截图、设备/视口、状态或源码位置。
- 对具体用户任务的影响。
- 建议的设计或实现变化及理由。
- 修复后应如何验证。

不要报告“看起来不够现代”这类不可证伪结论。把它改写成可观察事实，例如：“主要动作与次要动作使用相同尺寸和对比，可能增加用户辨认下一步的成本。”
