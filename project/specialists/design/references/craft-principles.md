## 先选择设计语域

先判断界面的主要语域，不要用同一套默认值覆盖所有产品：

| 语域 | 主要目标 | 优先考虑 |
| --- | --- | --- |
| 品牌 / 营销 | 形成记忆、传递价值、促成一个主要行动 | 叙事、内容节奏、视觉 signature、可信度 |
| 产品 / 工具 | 高频完成任务、理解系统状态、减少错误 | 信息密度、可预测性、状态、恢复、效率 |
| 数据 / 运营 | 快速扫描、比较、下钻和采取行动 | 对齐、数字排版、筛选、层级、异常信号 |
| 原生客户端 | 符合设备心智、输入和系统行为 | 平台导航、窗口/安全区、键盘或触摸、离线 |
| 嵌入式 / 大屏 | 在距离、光照、手套或受限输入下可靠操作 | 可读尺寸、强层级、大目标、危险动作保护 |

同一产品可以跨语域，但每个页面应有一个主语域。例如官网首页偏品牌，后台设置偏产品，监控大屏偏数据。

## 建立有依据的方向

从产品世界中取材：用户使用的对象、环境、语言、工具、材料、数据形态和行为节奏。不要先选“极简”“玻璃拟态”或“赛博朋克”，再把产品塞进去。

一个完整方向包含：

- **Thesis**：界面应让用户感到什么，并通过什么具体方法实现。
- **Signature**：一个能代表产品的可复用特征，而不是每处都抢眼。
- **System**：颜色、排版、空间、形状、图像和动效如何共同表达 thesis。
- **Restraint**：哪些区域保持安静，让 signature 有效。
- **Risk**：方向可能损害可读性、性能、信任或平台熟悉度的地方。

用户要求比较或确需比较才能作决定时，才探索多个方向。方向之间至少改变两个结构轴，例如内容节奏与排版、信息密度与导航、图像策略与空间结构；只换主色不算新方向。

## 信息层级与布局

- 让屏幕目的和当前状态在第一次扫视中可辨认。
- 每个普通任务状态只设置一个主导动作；对称选择必须明确表达为选择，而不是强行降级其中一项。
- 用位置、尺寸、留白、对齐和对比建立层级，减少用边框、卡片和颜色补救弱结构。
- 让结构表达真实关系。编号只用于真实顺序，分组只用于真实归属，分隔只用于真实边界。
- 让密度匹配任务：运营工具可以紧凑，首次引导需要呼吸空间，危险确认必须集中注意力。
- 优先流式、内容驱动的尺寸；固定高度只用于已知媒体或严格受控容器。
- 对宽屏定义内容最大宽度和多栏逻辑，对窄屏定义折叠顺序而非简单缩小。

## 排版

- 先定义角色，再选字体：display、body、UI、data/code 各自承担什么任务。
- 现有项目优先复用字体和 type tokens；不要为追求新鲜感引入额外下载和许可证风险。
- 用有限且清晰的字号、字重、行高和字距层级，避免每个组件拥有自己的排版值。
- 正文优先保证可读行长、行高和缩放；数据优先考虑等宽数字和对齐。
- 大标题、全大写、极细或极宽字形必须有语义和可读性理由。
- 用真实长文本、中文、英文、数字、错误信息和本地化扩展测试排版。

## 颜色与深度

- 以语义角色建模：canvas、surface、elevated、text、muted、border、accent、success、warning、danger、focus。
- 先确定中性色和文本关系，再决定强调色；强调色是稀缺资源。
- 不把颜色作为状态的唯一信号。配合文字、图标、形状或位置。
- 在项目支持范围内验证浅色、深色、高对比和禁用状态；不要通过降低透明度制造不可读文本。
- 用边框、色差、阴影和模糊表达一致的层级模型。不要混用多个互相冲突的深度语言。
- 渐变、透明、玻璃效果或纯黑白不是天然好坏；只有与产品语义、内容对比和性能相符时才使用。

## 组件与交互

- 组件表达稳定的行为和语义，不只是相似外观。
- 用 token 和变体处理有限差异，避免 boolean props、页面覆盖和嵌套卡片不断增长。
- 明确 hover、focus、pressed、selected、loading、disabled、error 和 success 状态。
- 每个错误提供可操作的恢复；每个空状态指出下一步；每个 disabled 状态解释原因。
- 表单使用持久标签、就近验证和清晰提交反馈；不要把 placeholder 当标签。
- 危险动作说明对象和后果，并使用合适的撤销、二次确认或权限保护。
- 让交互目标适合实际输入方式：鼠标精确不代表触摸、遥控器或手套也精确。

## 动效

- 只为因果、空间连续性、状态变化或注意力服务。
- 优先一个编排清楚的关键时刻，而不是到处分散动画。
- 让进入、退出和状态转换方向一致，持续时间与距离匹配。
- 不让动画延迟关键内容、错误或危险提示。
- 提供 reduced-motion 路径；任务完成不能依赖动画。
- 先验证低性能设备和长列表，再增加模糊、大面积滤镜或持续背景效果。

## 内容、图像与图标

- 使用接近真实长度和语义的内容；占位文案会掩盖层级、换行和状态问题。
- 控件文案描述结果，例如“保存更改”，不要使用含糊的“提交”或“继续”。
- 错误文案说明发生了什么以及如何恢复，不责怪用户。
- 图像承担叙事、说明或识别任务；纯装饰图像不得破坏信息层级和性能。
- 图标使用项目既有图标体系；语义不熟悉时配合文字。
- 不用 emoji 冒充产品图标，除非产品语言明确需要 emoji。

## 避免模板化

不要维护绝对风格黑名单。检查一个决定是否只是模型默认：

- 字体、紫蓝渐变、三等分卡片、胶囊标签、bento、巨大圆角或玻璃效果是否与任何同类产品都能互换？
- 每个区块是否都被包进相同卡片，导致结构和重要性消失？
- 是否用装饰性编号、eyebrow、图标方块和渐变代替真实内容结构？
- 是否为了“高级感”牺牲正文对比、目标尺寸、性能或平台熟悉度？
- 是否在没有品牌理由时复用了最近一次项目的视觉方向？

若答案为是，回到产品世界和主要任务重新推导。若一个常见模式确实最适合当前任务，保留它并说明理由；“常见”不等于错误。

## 质量底线

无论选择何种风格，都必须满足：

- 主要任务、当前状态和下一步动作清晰。
- 响应式或自适应行为明确，不发生非预期截断和横向滚动。
- 键盘、焦点、触摸目标、屏幕阅读器和字体缩放得到处理。
- loading、empty、error、disabled、permission 和 offline 状态按实际产品需要覆盖。
- 颜色对比、动效降级和错误恢复可验证。
- 公共 token、组件和项目现有设计规范与实现保持一致。
