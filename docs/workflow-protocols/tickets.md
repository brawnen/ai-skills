# 可交接任务与阻塞边

从已有规格、明确计划或任务讨论出发，复用已确认的业务术语和决定。缺关键业务判据才返回需求澄清；已有代码与文档能回答的事实自行读取。

## 核对任务归属与标题

按项目约定打开原始工作项或仓库内的任务台账。核对来源平台、仓库或项目空间、稳定编号和当前标题，再用工作区的 Git 根目录、远端或项目已记录的映射核实实施目标。集中管理工作项的项目可与代码仓库不同，交接时写明二者的对应关系。只给短编号时先在指定项目查找；出现重号、标题与请求明显冲突或来源不可读时，列出具体差异，请用户澄清后再实施相关任务。直接给出的明确需求无需创建任务编号。

## 拆分与关系

每项任务交付一条可独立验证的行为，覆盖其真正涉及的层，不为 API/CLI 强行增加 UI。广泛机械迁移采用 expand–contract；无法独立保持可用时明确集成分支和最终验证点。

沿用项目 tracker/文档位置。没有约定时采用仓库 Markdown；只有需要独立领取时才一项一工件。已有任务更新原工件，不复制第二份进度。外部 tracker 写入、关闭父任务和推送远端复用相应授权，生成本地草案不等于批准外部操作。

父子关系表达范围归属，阻塞关系表达开工所需的前置交付。先读取来源任务已有的子项和依赖，按实际缺口补齐。来源是现有工作项且平台支持子项时，挂到该父项下；来源只有规格时，保留规格指针。平台支持原生阻塞边时，用真实 ID 建立关系，核对方向（前置 A 阻塞后续 B）。两类能力分别判断，只有平台缺少某一类时，才在项目既有台账或任务正文记录该类指针。使用原生关系后省略正文里的同义清单。

获准发布后读回父项、子项和阻塞方向；部分成功或重试时复用已创建的 ID，只补缺失关系。仅获准拆分或平台写入受限时，交付待建立的关系并标明状态。

每项至少携带：

- 稳定 ID、行为交付物、spec/AC 与必要决定的指针。
- 真正阻止开工的前置任务，沿用上述关系来源；同属一个父项或编号相邻均不足以推定阻塞。
- 允许范围、公共接口与共享写入区域；不把现有文件位置写成永久设计约束。
- 验证入口、独立预期、完成门禁与证据位置；缺环境时如何报告。
- 项目需要时的责任人和状态，依项目既有约定维护。

无阻塞任务形成 ready frontier。共享 schema、接口、配置或同文件写入可能需要先明确契约或串行集成；没有显式边不自动证明可并行。提交任务前检查重复 ID、未知/自依赖、环和相互矛盾的状态。

并行调度需要快照时，可由主 tracker 派生 JSON 任务图供随入口提供的 `scripts/check-task-graph.py` 校验。它不是第二份 tracker；每次调度前核对来源与集成结果。格式如下，source 为真实任务指针，done 仅表示本次完成门禁已满足：

```json
{"schema_version":1,"spec":"spec-path-or-issue","tasks":[
  {"id":"A","source":"ticket-A","blocked_by":[],"status":"pending"},
  {"id":"B","source":"ticket-B","blocked_by":["A"],"status":"pending"}
]}
```

状态支持 pending、running、done、blocked。done 的判据由项目确定；需要集成的任务必须已在集成版本验证才能标 done。完成条件是任务可离开原会话被领取、依赖真实、验收可运行；范围与拆分已获授权时直接生成，不强制再询问一次颗粒度。
