# 需求澄清、价值切口与领域术语对齐

## 目标与模式

用同一套决策树访谈引擎处理四类紧密关联的前置任务。意图明确时直接选择或组合，不额外反问模式：

- **压力测试**：用户要求 grill、挑战假设、发现盲点或检查计划；暴露关键隐含假设与最小可行切口，不默认写需求文档。
- **需求收敛**：用户要求梳理需求、比较方案、定义成功或形成需求契约；产出可决策、可验收、可交接的需求说明。
- **领域术语与状态建模**：当业务概念同义/混用、实体身份或状态生命周期不变量含糊，或用户明确要求统一领域语言时，对齐 canonical terms、状态转移与上下文边界，按需更新 `GLOSSARY.md` / `ADR`。
- **混合模式**：先挑战想法与切口，再复用已确认结论收敛需求与核心领域词汇，避免重复访谈。

## 共同流程

1. 确认范围、模式和期望产物；只有模式会实质改变结果且无法从表述判断时才询问。
2. 先读取用户材料及仓库已有的 `README`、`GLOSSARY.md` / `CONTEXT.md`、`GLOSSARY-MAP.md`、ADR、schema、接口、代码或可信外部资料。能查证的事实绝不反问；缺少来源时说明缺口并请求材料，不把事实查证伪装成用户选择题。
3. **产品价值与最小切口审视（针对 0→1 新产品或重要新功能，借鉴 YC `/office-hours`）**：
   - **现状替代基线**：先弄清目标用户今天没有这个功能时用什么笨办法凑合解决（Excel、手工、旧工具或直接不做），痛点是否真实到值得迁移；
   - **20% 首日核心切口**：识别如果砍掉 80% 周边锦上添花功能，哪最小端到端闭环能让用户第一天就感受到不可替代的核心价值，防止单兵/小团队陷入自嗨式大而全开发。
4. **领域概念与边缘场景攻击（当存在术语/状态歧义时）**：
   - 区分易混名词（如 User / Account / Customer、Cancel / Close / Disable / Refund）、实体身份 vs 值对象、命令（期望动作）vs 事件（已发生事实）；
   - 状态名必须写明业务含义、进入/离开不变量与禁止转换，并用具体边缘场景攻击定义：**部分成功、重复提交、并发/重试、跨租户、过期、退款/撤销与历史存量数据**；发现业务描述与现有代码/数据库冲突时呈现证据请用户拍板。
5. 建立带前置依赖的决策树，每轮计算 `frontier`：只包含前置决策已闭合、现在可独立回答且必须由用户判断的问题。依赖问题留到后续；子代理后台查证源码事实时仅挂起依赖该事实的下游分支，不阻塞已就绪决策。
6. `frontier` 为空时直接产出。存在待拍板分支时，每轮优选信息增益最高或阻塞面最大的 **1–3 个问题**（明确要求密集访谈时可扩大）。编号提问，一题一决策；每题给推荐答案、理由及备选项对价值/范围/风险的影响，**措辞尽量让回复“是/同意”即代表采纳推荐方案**。
7. 用户回答后更新决策树并重算 `frontier`，维护 `已确认`、`推断`、`待确认`、`未验证` 状态（推荐项未经确认不得自动升级）。存在实质不同路径时给 2–3 个方案，只比影响决策的差异。

## 停止条件与产物

- **压力测试**：关键假设与切口已暴露时，直接输出已确认决策、脆弱假设、主要风险、最小验证切口与开放问题；除非要求，不写 PRD/spec。
- **需求收敛**：关键分支闭合或明确标为待决策后停止，按领域裁剪覆盖：背景与目标/非目标、核心场景与现状基线、核心术语与关键状态约束（有歧义时）、推荐方案与范围取舍、失败语义与独立验收标准、未覆盖风险与前置条件。
- **领域文档落点（仅在用户要求落地或项目已有词汇表需同步时写入）**：
  - 无既有词汇表时不提前建空模板；新建推荐 `GLOSSARY.md`（多上下文配合 `GLOSSARY-MAP.md`），已有 `CONTEXT.md` 原位沿用，保持实现无关；
  - 仅当决策同时满足“难回退、缺上下文令人意外、存在真实取舍”三条件时才建议记录 ADR，不因概念建模自动引入重型 DDD 代码框架（Aggregate/Repository/Event Sourcing）。

## 边界

- 不因普通任务存在一个可合理假设的小歧义就启动完整访谈；不把整棵决策树一次抛给用户。
- 用户只要求讨论、压力测试、术语梳理或需求说明时止于对应产物；执行步骤交回宿主原生计划或后续规格阶段。
