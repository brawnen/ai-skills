# 模块形状与测试缝

模块是通过接口提供行为的单元。接口包含调用方必须知道的签名、顺序、配置、错误及性能特征；深模块通过较小接口承载较多行为。缝是可替换行为的边界，适配器填入该边界；局部性关注一次变化及验证是否集中。

判断取决于真实变化与调用成本，不取决于文件数、接口数或采用了多少设计模式。删除某模块后复杂度若散落到多个调用方，说明它可能有封装价值；若只是消除透传，则可能可以简化。

优先稳定公共行为的测试入口，保留必要真实内部链路；外部或远程依赖才按契约隔离。测试困难时检查编排边界，不只把实现拆成易测但不能捕捉原始缺陷的小函数。

控制内部复杂度与 AI 冗余代码的三条抓手：
- **边界校验集中化**：只在系统外部边界（HTTP、CLI、配置、第三方回调与外部存储读取）做解析和防御性校验；一旦转为内部有效类型，内部模块直接信任类型，不在调用链层层重复判空或兜底。
- **非法状态不可表达**：优先用强类型、判别联合和语义包装类型在编译期消除非法组合，不靠散文注释或隐含约定维持不变量。
- **先拆离共享状态再串行化**：并发或多任务设计优先消除不必要的共享可变状态，仅在确有单一共享写入者时才引入锁、队列或事务串行化。

根据实际变更方向选择局部设计，说明收益、影响、兼容和验证。既有系统的广泛候选发现属于 scan-architecture，不把一次具体设计或代码审查扩大成全库重构。
