# 基于证据的环境复盘

读取用户指定会话/运行的原始材料；未指定时使用当前会话。无法获得原始记录时区分已观察与推断，不仅凭总结归因。只读分析不自动实施改动。

对每个反复发生或后果明显的问题，先还原当时的请求、预期和结果。若某个 skill 应负责这件事，核对当时可用的版本、触发描述、调用策略及实际会读取的协议，再查会话或工具记录，看执行走到了哪一步。版本或调用记录缺失时标为未知；当前源码只能说明今天的行为约定。普通宿主任务也可直接定位到项目。

| 核对环节 | 怎样选择改进位置 |
| --- | --- |
| 触发条件 | 比较原始请求与当时的路由、安装范围、显式调用要求。证据表明应该进入却被条件排除时，调整对应入口或路由。仅凭日志没提到 skill，不足以认定漏触发。 |
| 执行协议 | 对照当时正文、引用和实际操作，找出哪一步缺失或含糊，足以改变结果。若步骤已明确而本次漏做，记录执行偏差，核查原因。 |
| 项目接线 | 从实际命令或 CI 作业追到检查器、依赖和目标断言，以具名结果核对是否执行。手工可跑、日常入口却跳过的检查，修在项目脚本、配置或 CI。 |

可以同时发现项目缺陷和方法上的预防机会，分别给出证据。建议前再读现行版本，已有修正且对照验证有效的标为已解决；仍有缺口的才提出最小改动和可以区分修复前后的验证。

围绕真实重复成本和错误找改进：

- 导航：哪些查找耗时且已有事实难发现？优先补条件指针，避免复制配置清单。
- 自动检查：先读现有 lint/type/test/CI，分清缺检查、未接线和已存在但失效；机械错误优先修确定性检查。
- 判断标准：跨文件一致性、边界选择等不可机械判断的内容才进入项目规范，避免全放在 AGENTS。
- 工具与信息：昂贵的重复调用、过量输出、缺日志/只读访问，是否有更短且可信的反馈。
- 指令精简：哪些指令未改变行为或已过时？用对照证据支持删减，不凭一次主观感受宣称省 token。

必要时读取 authoring.md。按影响排序给出候选：原始证据、问题机制、改进位置、最小动作、验证方法及适用范围。区分项目检查/规范、共享 skill 方法和用户全局偏好，不能把某项目局部错误提升为全局禁令。

完成条件是给出可审查候选。已有明确授权可实施对应范围并复验；全局规则、外部账号/工具或其他项目变更不能从一次复盘推导授权。不要自动创建定时任务、安装 MCP 或写入宿主记忆。用户明确要求保存复盘时沿用项目载体。
