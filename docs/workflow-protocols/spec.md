# 实施规格

输入是已有需求、决定与相关项目事实。复用目标、非目标、必须保留的行为和已授权范围，不重新扫描完整仓库或重复访谈。无法查证且会改变业务含义的缺口才交给用户决定。

按需要说明模块/部署边界、状态拥有者、公共接口、失败语义、数据与兼容顺序；设计判断不明确时读取同目录 `architecture-design.md`，跨部署兼容或异步状态风险时读取 `cross-boundary-design.md`。没有真实取舍不新建 ADR。

业务规则与验收字段以 `docs/delivery-artifacts-spec.md` 为准：独立预期、前置角色和数据、真实入口、副作用、验证层级及替身边界。已有测试缝优先，不以“所有层都有测试”代替必要覆盖，也不从实现反推期望。

## 界面设计就绪检查（联动 `x-ui`）

制定规格或从规格进入前端/客户端编码前，检查任务是否涉及 **Web App、手机 App 或后台管理系统的 0→1 新页面、重要交互流程或视觉改版**：

- **已有就绪设计时直接继续**：纯后端/CLI 任务、已有明确设计稿、或在项目成熟 `DESIGN.md` / 组件库内做方向已定的常规增改，直接复用既有规范推进，不增加多余步骤。
- **缺少设计定调时主动进入 `x-ui`**：不能只因后端接口或业务规则写完了就直接盲写简陋的默认前端界面。主动调用全局 `x-ui`——用非术语通俗对焦 + 2~3 套可视化首屏小样引导用户选定视觉方向与布局结构（若纯属验证某个复杂状态/技术可行性，可配合 `prototype.md` 做最小实验）。
- **设计决定回写规格**：将确认的页面信息层级、平台适配要求（桌面响应式 / iOS & Android 安全区与原生导航 / 后台表格与筛选交互）、必配状态（加载、空数据、就近报错、无权限）及所需接口字段同步更新到 spec 与 `DESIGN.md` 中。用户保留审美选择权时等待确认小样后再展开全量页面编码；只要求输出规格文档时，明确标出界面设计缺口与下一步 `x-ui` 建议。局部界面待确认不阻塞无依赖的后端数据层开发。

## 实施与交接

同一会话连续实施、无需独立领取/恢复且相关界面设计已就绪时，规格可内联简短实施顺序，直接进入宿主实施。需要跨人/会话交接、维护阻塞边或并行执行时才由 `x-tasks` 生成独立任务工件。不设切片数量或 token 阈值；已有有效 spec 只补实际缺口。

完成条件：必要需求、界面方案、技术契约、验收判据及未决项足以让当前实施者或接手者继续。区分已确认、授权内代理决定、推断和未验证。只要求规格时到此停止；已授权完整交付时复用授权推进，不新增阶段审批。
