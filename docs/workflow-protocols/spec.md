# 实施规格

输入是已有需求、决定与相关项目事实。复用目标、非目标、已对齐的领域术语/状态与已授权范围，不重新扫描完整仓库或重复访谈。无法查证且会改变业务含义的缺口才交给用户决定。

按需要说明模块/部署边界、状态拥有者、公共接口、失败语义、数据与兼容顺序；设计判断不明确时读取 [架构参考](architecture-design.md)，跨部署兼容或异步状态风险时读取 [跨边界设计](cross-boundary-design.md)。没有真实取舍不新建 ADR。

## 独立验收与测试缝得失对比

业务规则与验收字段以 [交付产物契约](artifacts.md#1-实施规格) 为准：独立预期、前置角色和数据、真实入口、副作用、验证层级及替身边界。

- **候选测试缝（Seam）得失对比**：当存在多个可选测试切入层（如纯函数入口 vs 服务编排层 vs 真实 HTTP+DB 集成入口）且取舍不明显时，为每个候选测试缝给出一句话对比——**「它能捕获什么缺陷、又会漏掉什么风险」**，选择能覆盖本次真实风险的最窄稳定公共入口，不盲猜层级，也不以“每层都写 mock 测试”冒充真实链路覆盖。
- 期望值必须来自需求、独立示例或外部事实，禁止调用生产算法生成 expected。

## 界面设计就绪检查（联动 `x-ui`）

制定规格或从规格进入前端/客户端编码前，检查任务是否涉及 **Web App、手机 App 或后台管理系统的 0→1 新页面、重要交互流程或视觉改版**：

- **已有就绪设计时直接继续**：纯后端/CLI 任务、已有明确设计稿、或在项目成熟 `DESIGN.md` / 组件库内做方向已定的常规增改，直接复用既有规范推进，不增加多余步骤。
- **缺少设计定调时主动进入 `x-ui`**：不能只因后端接口或业务规则写完了就直接盲写简陋的默认前端界面。主动调用全局 `x-ui`——用非术语通俗对焦 + 2~3 套可视化首屏小样引导用户选定视觉方向与布局结构（若纯属验证某个复杂状态/技术可行性，可配合 [原型实验](prototype.md) 做最小实验）。
- **设计决定回写规格**：将确认的页面信息层级、平台适配要求（桌面响应式 / iOS & Android 安全区与拇指热区 / 后台表格与筛选交互）、必配状态（加载、空数据、就近报错、无权限）及所需接口字段同步更新到 spec 与 `DESIGN.md` 中。用户保留审美选择权时等待确认小样后再展开全量页面编码；只要求输出规格文档时，明确标出界面设计缺口与下一步 `x-ui` 建议。局部界面待确认不阻塞无依赖的后端数据层开发。

## 实施与交接

同一会话连续实施、无需独立领取/恢复且相关界面设计已就绪时，规格可内联简短实施顺序，直接进入宿主实施。确需跨人/跨会话交接、维护真实阻塞边或并行调度时，衔接 `$x-dev` 的任务协议（`<x-dev>/references/tickets.md`）生成独立可领取任务工件。不设切片数量或 token 阈值；已有有效 spec 只补实际缺口。

完成条件：必要需求、界面方案、技术契约、测试缝与验收判据足以让当前实施者或接手者继续。区分已确认、授权内代理决定、推断和未验证。只要求规格时到此停止；已授权完整交付时复用授权推进，不新增阶段审批。
