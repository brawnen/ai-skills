# 实施规格

输入是已有需求、决定与相关项目事实。复用目标、非目标、必须保留的行为和已授权范围，不重新扫描完整仓库或重复访谈。无法查证且会改变业务含义的缺口才交给用户决定。

按需要说明模块/部署边界、状态拥有者、公共接口、失败语义、数据与兼容顺序；设计判断不明确时读取同目录 `architecture-design.md`，跨部署兼容或异步状态风险时读取 `cross-boundary-design.md`。没有真实取舍不新建 ADR。

业务规则与验收字段以 `docs/delivery-artifacts-spec.md` 为准：独立预期、前置角色和数据、真实入口、副作用、验证层级及替身边界。已有测试缝优先，不以“所有层都有测试”代替必要覆盖，也不从实现反推期望。

## 界面设计就绪检查

初版规格形成后、拆解或实施相关界面前，检查是否涉及新页面、重要交互流程或视觉方向变化。已有设计稿、设计系统和页面约定足以支持当前改动时直接复用；纯后端、方向已定的机械实现或简单样式修正直接继续，不另造原型或设计文档。已有 spec 的恢复任务也检查实际缺口。

存在上述界面设计缺口时，主动向用户说明下一步需要页面/交互设计，不能只因技术规格完整就跳到业务界面编码。形成可查看的页面方案，覆盖关键用户路径、页面布局及适用的加载、空、错误和权限状态；按风险选择线框、设计稿或可交互页面，不要求全部形式。项目已引入 design 时复用其约束与能力路由，否则使用宿主可用设计能力，不自动安装第三方 skill。prototype 用于通过可运行实验回答尚不确定的交互或状态问题，不是每次网页设计的必经入口；未安装时可由宿主完成最小实验，未实际运行的草案标为未验证。

用户保留方案选择权时先展示方案并等待选择；已授权自主设计时在约束内继续，不新增固定审批。只要求规格时，在交付中指出设计缺口、影响范围和建议下一步，不擅自制作原型或实施。设计决定沿用项目记录位置，在 spec 中引用并更新受影响的契约、验收与实施顺序；不复制维护整套视觉规范。局部缺口只阻塞依赖它的界面工作，其余已授权工作继续。

## 实施与交接

同一会话连续实施、无需独立领取/恢复且相关设计已就绪时，规格可内联简短实施顺序，直接进入宿主实施。需要跨人/会话交接、维护阻塞边或并行执行时才生成独立 tickets。不设切片数量或 token 阈值；已有有效 spec 只补实际缺口。

完成条件：必要需求、方案、验收及未决项足以让当前实施者或接手者继续。区分已确认、授权内代理决定、推断和未验证。只要求规格时到此停止；已授权完整交付时复用授权推进，不新增阶段审批。
