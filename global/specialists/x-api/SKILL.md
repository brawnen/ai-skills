# 前后端 API 契约

将 [API（应用程序接口）默认规范](references/api-conventions.md)作为可复用基线；每次应用时读取。用户要求“按我的 API 规范”或明确调用本 skill 时，直接沿用，不重新访谈已规定的格式和错误策略。已有项目的明确契约及用户本次决定优先；这套约定不是唯一行业标准。

## 应用方式

1. 从现有规格、接口描述、公共请求层及生成配置中识别真实契约。新项目直接采用基线；旧项目先列差异，不因调用 skill 自动迁移全部接口。
2. 仅收敛影响当前范围的差异：现有 HTTP／业务错误策略、成功码、币种及最小单位、比例精度、业务时区、分页方式（页码或游标）、流式事件结构、写幂等约定及认证入口。可从项目确认的事实不反问；无冲突时明确采用默认值后继续。
3. 更新项目已有的公共接口契约，按需补充机器可读的 OpenAPI（开放接口描述规范）。用户只要求约定时停在规范；要求接口设计时再描述相应路径和数据结构，不为填全接口猜业务规则。
4. 工程已建立且任务包含落地时，绑定实际生成／校验工具、精确版本及命令，复用公共请求层；生成类型、领域模型和数据库结构保持边界。不默认特定语言、框架或生成器。

只有尚未确定且会改变行为或兼容性的差异才需要用户选择。已有 HTTP 语义型错误方案可以继续使用；明确差异及适配，不能静默改成业务拒绝 HTTP 200，也不为新项目重新比较两套方案。

## 关键约束

- 业务拒绝与认证／协议／系统错误分别处理；没有响应就没有真实 HTTP 状态。框架自动校验不得悄悄改变约定的错误分类。
- `request_id` 关联请求和日志，不承担业务身份、防重或写入结果确认。非天然幂等的写接口通过显式业务唯一键或 `Idempotency-Key` 处理重试，超时不统一盲目重发。
- 流式响应（SSE / NDJSON）在响应头发出 `200` 后中途失败时，必须发送结构化错误事件帧并携带同一 `request_id`，不得静默断流冒充正常结束。
- 金额字符串只定义传输表示；保留内部精确计算、业务单位和舍入规则。未知值、零值、字段缺省分别定义。
- OpenAPI 描述结构，业务规则仍归项目规格；生成或编译通过不能代替真实入口、权限、副作用及兼容验证。

## 交付与验证

优先更新现有权威文件；缺少入口且确需跨会话复用时再建一份公共契约，不强制每次另写报告。交付采用的基线、项目差异、相关文件、已验证结果及剩余缺口。

按实际产物检查：文档／JSON示例可解析；OpenAPI 可被选定工具解析和生成；有实现时验证真实成功、业务拒绝、认证／权限拒绝、流式中断错误兜底及适用的旧客户端兼容。只生成规范时，后几项明确为未运行。
