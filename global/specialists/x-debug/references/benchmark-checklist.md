# 性能测量与基准反自欺清单

产出性能数字（PR 前后对比、性能回退定性、方案/库选型压测）时读取本清单。每项结论以运行证据作答，不凭代码臆测。仅需快速粗估（ballpark）时可单次运行，但仍必须核对第 4、7 项并注明仅跑一次；**技术选型对比绝不按粗估处理**。

## 测量前准备

- 先写下要验证的具体主张（例如“6 万行导出 p50 缩短 30%”），后续 7 问直接检验该主张。
- 读懂测量脚本：确认它究竟计时什么、计数什么、忽略了什么。
- 检查本机负载（`uptime`）与核心数；若机器繁忙且无法清空，采用 A/B 交错运行并在报告中如实说明噪声。

## 7 问核查

1. **为什么不能再快一倍？（定位瓶颈）**：先在单独的 profiling 运行中找出真实 limiter（CPU、runtime profiler、I/O wait、syscall 或压测客户端本身），将热点映射到源码；不要把带 profiler 开销的采样直接当成基准数字。改完没提速时，先看 limiter 解释原因。
2. **双方是否按生产等价调优？**：必须使用 release 构建、生产配置与环境变量、一致的批处理/事务/连接池/冷热缓存及同版本数据。若一方跑在默认未调优配置（如逐行提交、debug 构建、缺索引），比的是配置而不是实现；无法调优时不得宣布胜者。
3. **有没有违背物理/算术上限？**：核对带宽、核心数和阿姆达尔定律（去掉占比 10% 的模块最多提速约 11%）。超过理论上限的数字通常测到了缓存命中、空操作或 bug。
4. **有没有静默报错或被拒？**：统计失败数与非成功响应，并验证输出内容正确而非仅有返回。快速拒绝往往跑得很快，超时重试则会拉垮尾延迟。
5. **能否稳定复现？**：双方至少各跑 5 轮并交替执行（A, B, A, B…）抵消预热、缓存和系统漂移；报告中位数与波动区间。差值小于波动区间时判为无明显差异。
6. **对真实端到端是否重要？**：微基准旁边必须给出用户等待的端到端路径数据及该环节占比（只占总请求 1% 的函数优化到零也只能提速 1%）。
7. **目标工作真的在计时窗口内发生了吗？**：确认请求真打到服务端、数据真落盘/读取、返回值真被消费，防止惰性求值、未 await 的 Promise、JIT 死代码消除或静默超时制造假数字。

## 结论与门槛

- 结论先行：`更快 / 更慢 / 无可测差异 / 结论不充分（inconclusive）`，附单位、运行次数、中位数与范围以及定位到的 limiter。
- 无法指出 limiter、任一方未按生产等价调优，或未能核对第 4、7 项时，**必须判为结论不充分并列出缺口**，不得据此宣布优化有效或拍板选型。
