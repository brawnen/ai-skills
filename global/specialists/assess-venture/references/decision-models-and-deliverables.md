# 决策模型与交付模式

## 一、整条推导链

综合任务默认沿这条链路工作，按用户问题裁剪：

```text
决策问题与非目标
  → 现状工作流、替代方案与基线
  → 内部证据、现场证据和外部证据
  → 用户任务链、能力链与最弱环
  → 市场、竞品、合作和进入条件
  → 首个可收费产品与单位经济
  → 技术责任边界、架构与验证闭环
  → 分阶段投资、阶段门和止损
  → 批准 / 调整 / 暂缓 / 停止
```

不要先写完整技术愿景再找商业理由。也不要先用巨大 TAM 证明某个具体方案可行。每一层只使用前面已成立的证据，并把未闭合处保留为条件。

## 二、可行性矩阵

按项目裁剪以下维度：

| 维度 | 核心问题 | 常见证据 |
| --- | --- | --- |
| 问题与需求 | 痛点是否高频、昂贵且由明确责任人承担 | 现场流程、工时、错误、等待、返工、采购记录 |
| 产品与工作流 | 最小产品是否嵌入真实流程并改善结果 | 用户任务、当前工具、审核和交接链 |
| 数据 | 输入、真值、版本、授权和反馈是否可得 | 样本链、字段字典、标注和数据协议 |
| 技术 | 各能力层能否分别验证，最弱环在哪里 | 基线、实验、原型、失败案例、接口和实物结果 |
| 生态与依赖 | 外部系统、设备、合作方和许可是否可控 | capability matrix、合同、测试环境、责任人 |
| 运营与采用 | 谁审核、维护、培训、处理异常和承担质量 | SOP、权限、支持成本、变更管理 |
| 安全与合规 | 数据、知识产权、责任和监管是否允许 | 授权、保密、审计、合规意见 |
| 商业 | 谁付钱、为什么现在付、毛利和回收是否成立 | 价格访谈、报价、试点、替代成本、经营数据 |
| 团队与治理 | 稀缺能力、决策权和资源承诺是否真实 | 人员、FTE、招聘、股东/合作协议 |

每个维度给出当前状态、决定性缺口、验证方法和对投资的影响。总体结论由最弱的决定性环节约束，不对各维度简单求平均。

## 三、商业模式与单位经济

### 首个可收费产品

必须具体回答：

- 用户、买方、预算拥有者和最终放行者分别是谁；
- 触发使用的工作和当前替代方案是什么；
- 产品交付什么可观察结果，不交付什么；
- 客户按什么价值单位付费；
- 为什么先买这一小段，而不是等待终局平台；
- 失败时怎样人工接管、退款、降级或停止。

### 收入与价值

候选收入结构可组合订阅、席位、站点、用量、项目、实施、支持、API、硬件绑定或结果分成。选择依据是价值归属、使用频率、交付成本、采购习惯和可审计性，不追求模式新颖。

单客户年度价值可按项目选择变量：

```text
节省工时
+ 缩短周期带来的产能或获单价值
+ 减少返工、材料、设备和质量损失
+ 新增收入或更高通过率
- 新增审核、集成、运维和切换成本
```

可承受年费受客户可获取价值比例和替代品价格约束。项目毛利还需扣除推理/算力、实施、客户成功、专用集成、专家服务和支持成本。

### 情景模型

至少列出会改变结果的变量，而不是只给总数：

- 目标账户与可服务比例；
- 获取速度、销售周期、转化和流失；
- 客单价、实施费和扩张收入；
- 每客户交付与支持工时；
- 研发、数据、集成、设备、合规和渠道成本；
- 毛利、现金消耗、回收期和下一轮资金点。

数据不足时保留公式、范围和待取数项。下行情景必须说明停止后仍剩下的数据、工具、接口、客户关系或低风险产品能力。

## 四、技术方案构建

### 从责任边界开始

技术图之前先定义：

- 输入事实、未知和冲突如何表示；
- 标准中间语义或领域对象是什么；
- 哪些计算和约束必须确定性、版本化和可测试；
- 哪些部分由外部合法接口执行；
- 谁对最终质量、安全或业务决定放行；
- 失败、低置信度、接口不可用和结果不合格时如何回退；
- 运行结果如何成为下一轮评测和学习数据。

常见但非强制的分层：

```text
多源输入
  → 证据定位与结构化语义
  → 知识/案例检索
  → 确定性规则、约束或求解
  → 候选规划与外部系统集成
  → 静态验证、仿真或沙箱
  → 人工审核与真实环境验证
  → 结果、缺陷和修订回填
```

不用大模型承担已有稳定公式，不让规则引擎猜测输入中不可见的信息，不绕过厂商私有格式和责任边界。编译、仿真、沙箱或离线指标通过后，仍要完成与项目目标相匹配的真实结果验证。

### 数据与评测

为每个案例关联：原始输入、结构化真值、人工决策、系统候选、规则/模型/接口版本、执行结果、缺陷和最终质量。按独立业务对象划分训练、验证和测试，避免修订版或同族样本泄漏。

指标至少覆盖：

- 关键字段、单位、对象和来源定位；
- 严重错误、冲突/未知检出和安全阻断；
- 约束正确、接口/编译/执行结果；
- 人工修改量、完成时间、返工和最终质量；
- 业务价值、付费和采用；
- 失败类型及其是否可通过数据、规则、流程或降级修复。

## 五、PoC 与阶段门

### PoC 冻结表

| 项 | 需要冻结的内容 |
| --- | --- |
| 决策问题 | PoC 结束后决定继续、调整还是停止什么 |
| 样本 | 数量、来源、独立性、难度和授权 |
| 输入/输出 | 格式、必填、证据和审核状态 |
| 基线 | 当前人工/软件的质量、时间和成本 |
| 指标 | 技术、业务、安全、人工和付费指标 |
| 通过线 | 必须通过与方向性指标分开 |
| 严重错误 | 即使平均分高也必须失败的行为 |
| 降级 | 低置信度、资料缺失、外部失败时的行为 |
| 依赖 | 数据、专家、设备、接口、环境和责任人 |
| 产物 | 可运行证据、评测、失败案例和决策建议 |

### 阶段门模板

```markdown
### Gx：<本阶段消除的不确定性>
- 进入条件：
- 验证活动：
- 可观察产物：
- 必须通过：
- 方向性指标：
- Go：
- Adjust：
- Stop：
- 通过后解锁：
- 停止后保留：
```

Go 不等于终局承诺，只解锁下一阶段。Adjust 应缩小场景、改变输入规范、补数据或改责任边界；不能在同一证据没有变化时无限重试。Stop 条件应在投入前约定。

## 六、交付模式

### 证据评估

适合回答“现有资料能证明什么”。结构：结论摘要、资料链、可读性与质量、对各能力的证据强度、缺口、最小实验、数据安全和下一步。

### 市场与竞品报告

结构：研究问题与日期、证据等级、市场任务链、竞争四类、能力/商业模式矩阵、关键威胁和机会、可被推翻的判断、验证清单和来源。

### 综合可行性与阶段投资报告

结构：一页决定、证据边界、现状与前置条件、分维度可行性、市场与商业、技术责任链、阶段路线、现金/资源、阶段门、风险、尽调和最终建议。

### 技术方案或 PoC spec

结构：决策问题、目标与非目标、用户和流程、输入输出、状态与失败、架构和数据、样本、指标、通过线、交付物、周期、人员依赖和 Go / Adjust / Stop。

### 投资决策简报

结构：本轮建议批准与不批准的事项、本轮资金购买的证据、资金释放条件、市场和付费缺口、团队治理、下行情景、尽调清单和下一次决策时间点。

产物结构是可选模块，不是固定目录。先复用已有事实源；同一数字或阶段判断不要在多份文档中手工维护彼此独立的副本。
