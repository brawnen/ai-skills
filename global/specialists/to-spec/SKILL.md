# 实施规格

把已有需求与项目事实转成能实施、验收和交接的契约。沿用项目 spec/任务载体；没有约定时采用仓库 Markdown。

## 判据与方案

先查相关实现、公共接口、测试设施、约束和现有决定；不要重复完整仓库扫描。只补会改变范围、实现方向或验收结果的缺口；业务取舍无法查证时由人决定，需要结构化访谈再选择 `to-decision`。

需要字段或示例时读取 [产物契约的规格部分](references/artifacts.md#1-实施规格)，按任务裁剪：

- 目标、非目标、不能改变的行为与来源；区分已确认、推断及待决策。
- 交接需要时给规则/场景编号，记录前置数据/角色、真实入口、预期、副作用、验证方式与持续回归要求。
- 预期独立于生产算法。固定值给实例，动态值给范围、不变量、关联关系或明确评分判据；不制造固定 ID/时间。
- 相关数据形状、状态拥有者、模块/部署边界、接口与失败契约；有实际取舍才记录 ADR。
- 公共测试缝、必要真实依赖及替身边界；计划局部、集成、E2E 的覆盖，不强迫所有场景走最高层。
- 有实际风险才展开迁移、兼容窗口、恢复与专项检查。

## 行为切片

每个任务形成独立可验证的行为和明确交付物，标出真正的阻塞边、覆盖场景及验证入口。能直接完成的任务不拆。广泛机械迁移不能独立保持可用时采用 expand–contract，或明确集成分支与最终验证点。

只在入口或旅程被改变时更新功能地图，不把文档更新变成每个切片的固定步骤。

已确认需求/验收和实施授权可复用，不因生成 spec 增加审批。用户要求只出方案时止于方案；存在未授权的新范围、关键业务决定或难回退方向时，先呈现可审查结果并暂停相应实施。
