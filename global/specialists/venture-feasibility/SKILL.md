# Venture Feasibility

## 目标

把研究转成可执行的投资或立项决定，而不是堆积资料。最终必须回答：现在能批准什么、不能批准什么、依据是什么、下一笔时间或资金由什么新证据解锁。

默认把可行性、市场、商业和技术视为同一条决策链的不同视角。用户只要求其中一项时，完成该项所需的最小闭环，不强制扩写完整报告。

## 入口模式

- **综合可行性**：从机会、现状、市场、商业、技术到阶段投资形成完整判断。
- **市场与竞品**：验证需求、替代方案、竞争边界和市场进入条件，不只罗列厂商。
- **商业模式**：定义首个可收费产品、买方与价值单位、收入和成本结构、单位经济及回收条件。
- **技术方案**：从真实输入、约束、失败和验证链构建架构、PoC 与阶段门，不把愿景直接画成终局系统。

意图明确时直接选择模式；只有决策对象、目标读者或产物会实质改变研究结论且无法从材料判断时才澄清。

## 开始前

1. 明确当前决策：谁要决定什么、时间范围、可投入上限、希望降低哪类不确定性。
2. 读取可访问的项目文档、原始资料、会议记录、数据样本、现有流程、实验和既有报告。能查证的事实不要反问。
3. 识别现状替代方案，包括人工流程、Excel、旧软件、外包、合作方和“不做”。新方案必须相对现状创造可测价值。
4. 确认保密、授权和数据边界。未经明确授权，不把客户资料、私有接口、内部成本或未公开设计上传到外部服务。
5. 市场、竞品、价格、政策和公司状态等时效性事实需要联网查证时，优先一手来源并记录发布日期与适用范围。

涉及证据盘点、外部研究、竞品或市场主张时，读取 [references/evidence-and-market-research.md](references/evidence-and-market-research.md)。形成综合报告、商业模型、技术方案或阶段门时，读取 [references/decision-models-and-deliverables.md](references/decision-models-and-deliverables.md)。

## 共同工作流

### 1. 建立决策问题与证据账本

先把愿景改写为可证伪的问题，例如“某类用户是否会为某个受控结果付费”或“在给定输入与合法接口下，最小端到端链是否能达到通过线”。为关键主张记录来源、时间、适用范围和证据状态。

统一使用：

- **已验证**：本轮从文件、数据、现场、代码、实验、合同或实物中直接核对。
- **用户确认**：用户给出的业务或合作前提；不自动等同于外部履约已验证。
- **推断**：由证据支持但仍需实验、访谈或交易验证的判断。
- **未验证**：当前材料无法回答。
- **待决策**：必须由投资人、业务、产品或技术负责人选择。

来源质量和证据状态是两个维度。官方宣传可以是高质量的一手来源，但仍只证明厂商公开声称了什么，不证明本项目已经实现或客户一定愿意付费。

### 2. 还原真实任务链

从原始输入到业务结果逐段还原：谁读取什么、做什么判断、使用什么工具、产生什么中间物、在哪里返工、最后由谁放行。区分人工工作时间、自然日等待、设备时间和外部依赖。

每段都回答：

- 输入与输出是否稳定、可获得、可授权？
- 知识来自显式规则、历史案例、隐性经验还是外部系统？
- 失败能否检测、解释、回退和人工接管？
- 当前基线如何测量，自动化后改善什么指标？

### 3. 拆解能力链并找最弱环

不要把“AI 能否完成”当成单一问题。按任务拆成理解、结构化、计算/规划、生成/执行、验证、物理或业务结果等串联能力；任何一层失败都不能把末端结果写成已通过。

明确责任边界：

- 模型适合不确定输入理解、检索、候选生成、解释和交互。
- 规则、求解器、验证器和编译器承担可测试的确定性、约束和执行语义。
- 外部厂商或平台承担其合法接口、专有格式和设备能力。
- 专家、现场实验或真实交易负责最终质量和价值放行。

从终局倒推必需能力，但按当前最弱证据安排投资。每个高风险假设必须映射到一个能产生新证据的实验、访谈、样本或合同交付。

### 4. 连接市场、商业与技术

- 竞品存在可以验证品类和预算，但也可能证明差异化空间已被占据；不能只取有利解释。
- 市场方向成立不等于市场规模、可服务客户数或付费意愿已验证。
- 首个可收费产品必须对应一个明确用户、工作流、可观察结果和价值单位。
- 定价要由客户价值、替代成本和交付成本共同约束；公开价格只能作为锚点。
- 技术架构必须服务于首个价值闭环、失败控制和数据回流，不以“使用大模型”本身作为方案。
- 护城河应落在难复制的配对数据、工作流嵌入、合法集成、质量闭环或渠道，而不是泛称“AI 能力”。

### 5. 设计最小完整验证与阶段门

PoC 必须是一条最小但完整的证据链，冻结样本范围、输入输出、人工基线、指标、通过线、失败行为和降级规则。视觉 Demo、离线准确率、编译成功、仿真通过或单一成功样例只证明相应局部能力。

阶段不要求固定数量，但每一阶段都要包含：

- 本阶段要消除的最大不确定性；
- 必需前置条件和责任人；
- 可观察交付物、测试样本和基线；
- 技术、业务、安全和付费指标；
- Go / Adjust / Stop 条件；
- 通过后解锁的范围或资金；
- 停止后仍可保留的资产。

优先释放“购买证据”的投入，再释放“建设平台”的投入。没有最小闭环、独立验收或付费证据时，不用长期路线图替代阶段门。

## 数字、成本与概率

- 准确率、自动化率、周期、成本、TAM、收入和 ROI 必须注明实测值、外部口径或规划区间，并列出关键假设。
- 样本不足时报告覆盖范围和失败类型，不发布虚假精确的泛化概率。
- 现金支出、非现金资源承诺和机会成本分开；合作意愿不自动折算成已交付资源。
- 情景模型至少说明基准、上行、下行的变化变量；没有输入事实时保留公式和待取数项，不编造完整五年数字。
- AI 辅助开发可以压缩通用软件工作，但不能无依据消除领域专家、数据治理、集成、设备、合规和质量责任。

## 交付

先给决策，再给证据和推导。按任务裁剪，通常从以下模块选择：

1. 当前建议：批准、暂缓或停止什么。
2. 评估对象、现状流程、替代方案和非目标。
3. 证据边界：已验证、用户确认、推断、未验证、待决策。
4. 市场、客户、竞品与进入条件。
5. 首个可收费产品、价值模型、收入结构和单位经济。
6. 能力链、技术架构、依赖、失败与验证闭环。
7. 分阶段路线、现金/资源需求、阶段门与止损。
8. 风险、尽调清单和一个最优下一步。

把“能证明什么、不能证明什么、还差什么”放在结论附近。新证据推翻旧判断时，更新事实源并检查所有受影响的摘要、数字、阶段门和派生文档，不维护互相冲突的平行结论。

## 边界与协作

- 用户只要求研究、分析或报告时，不自动启动开发、采购、外部访谈、试点、训练、融资或合作方协调。
- 需要通过分轮访谈压力测试想法或收敛 PRD/spec 时使用 `decision-clarification`；本 skill 使用已经取得的事实形成可行性判断。
- 用户明确要求自包含、可打印的正式 HTML 时，可使用 `formal-html-docs` 呈现结果；Markdown 仍是默认维护格式。
- 具体跨客户端、服务、API 或数据库的实施前架构评审使用 `review-cross-stack-change`；本 skill 负责机会层和方案层的证据、边界与阶段决策。
- 不用通用行业常识补齐客户事实，不把供应商意愿写成合同，不把局部技术成功写成业务成功。
