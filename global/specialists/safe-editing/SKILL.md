## 适用场景

- 修改 legacy、缺少测试或长期无人维护的代码
- 修改公共入口、共享配置、兼容协议或外部调用方依赖的行为
- bugfix、补丁或局部逻辑修改的影响面难确认、验证成本高或回滚困难
- 用户明确要求最小改动、不要重构或保护兼容性

## 不适用场景

- 普通低风险修改，影响面清楚且验证入口完整
- 全新功能 / 全新独立模块从零开发
- 用户明确授权"做一次大重构 / 大清理 / 现代化"
- 纯文档、注释、类型补全
- 大版本依赖升级（本身必然涉及面广，另走专项流程）

- 发现的 follow-up 在最终汇报中列为遗留风险，不顺手扩大当前改动

## Legacy code 识别信号

任一命中即按 Legacy 处理：

- README / git log 显示该模块 6 个月+ 无活跃维护
- 测试覆盖率显著低于项目平均
- 文件含明显过时模式（var、callback hell、jQuery、老协议、老规范）
- 用户主动标注"老系统 / legacy / 历史代码"

Legacy 额外要求：

- 默认保持现有行为和兼容性，修改前先识别高风险区域（老配置、公共入口、老事务）
- 尽量复用现有模式，不引入新框架、新范式、新依赖
- 不要假设老系统一定支持新工具链或新规范
- 不要改变外部接口行为，除非用户明确要求

## 范围风险信号

以下信号用于提高检查强度，不作为机械的文件数或行数阈值：

- 需要修改原计划之外的模块、公共入口、共享配置或根级脚本
- 需要引入新依赖、新架构模式或改变外部接口行为
- 无法从调用方、测试或运行入口确认影响面
- 变更无法局部回滚，或必须与多个模块同时发布

只有范围扩大改变了用户已确认的方案、风险或交付边界时才暂停确认；可验证的必要配套修改可以直接完成并在最终汇报中说明。

## 核心规则

1. 先定位与需求直接相关的文件、模块、函数或配置项。
2. 优先采用局部修复和最小闭环修改，不扩展成架构重构或全盘整理。
3. 只修改完成当前任务所必需的代码路径。
4. **复用现有模式**：修改前先 `grep` 找 2-3 处相似实现，沿用最近一次的写法，不写"教科书写法"。
5. 发现潜在更大问题，记录为遗留风险，不直接展开。
6. 收尾时说明范围控制、兼容性和未处理问题；本 skill 不定义独立汇报格式。

## 扩大范围的流程

如果分析后确认必须扩大用户已确认的范围，或需要引入新依赖 / 新模式：

1. 暂停执行
2. 显式输出：「原本只该改 X，现在要扩大到 Y，原因是 Z」
3. 等待用户回复确认才能继续

不允许"默认扩大"或"先扩大再说明"。

## 禁止事项

- 不要为了"更优雅"或"现代化"而扩大改动范围
- 不要混入无关格式化、命名调整、目录整理或依赖升级
- 不要轻易替换已有基础库、框架写法或项目模式
- 不要在一次任务中同时处理多个历史问题，也不要同时做功能修改和大重构
- 不要因为顺手就改 shared config、root config 或全局脚本
- 不要把"看起来不优雅"等同于"必须重构"
- 必须扩大范围或引入新依赖时，必须先按"扩大范围的流程"获得同意

## 交接

- 实现步骤和状态由 `task-todolist-execution` 管理，本 skill 不维护第二份 TODO。
- 完成汇报使用宿主 Agent 的原生格式，本 skill 只提供范围、兼容性和遗留风险事实。
