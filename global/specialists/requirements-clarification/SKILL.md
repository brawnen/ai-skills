# Requirements Clarification

## 目标与边界

把模糊需求变成可执行、可验证、可交接的已确认 spec。完成条件是决策和验收边界已确认，不是文档足够长，也不是代码已经实现。

- 需求已经明确并进入实施：不触发本 skill。
- 只需要说明当前代码如何工作：使用 `code-evidence-docs`。
- 用户要求只分析或先讨论：不写文件，只输出草案。
- 不默认进入实现或提交 Git。

## 工作流

1. 确认本次需要澄清的是目标、范围、方案、接口、流程还是验收标准。
2. 先读取 README、AGENTS、现有文档、接口、测试、配置和相关源码；能查证的事实不反问用户。
3. 区分四类信息：已确认、推断、待确认、未验证。
4. 一次只问一个会阻塞后续设计的关键问题，并给推荐答案和理由。
5. 存在多个可行路径时给 2-3 个方案，比较成本、风险、验证方式和回滚难度。
6. 先让用户确认关键决策，再落盘 spec；没有确认不得把推荐方案写成既定结论。
7. 自检目标、非目标、接口/数据影响、验收口径、未确认项和范围蔓延。
8. 明确下一步应进入实现、测试、排障、发布核对还是继续澄清。

## Spec 最低内容

- 背景、目标和非目标
- 已确认事实与待确认问题
- 推荐方案、必要的备选方案和取舍
- 接口、数据、流程与依赖影响
- 验收标准、自动化/人工验证和未覆盖风险
- 本次处理范围、非范围和进入实现的前置条件

章节应服从问题，不为填满模板而制造内容。正式需求或设计文档使用 `formal-html-docs` 的对应文档类型；README、AGENTS、轻量 ADR 和开发说明继续使用 Markdown。需要长期维护时可同时保留 Markdown 源稿和 HTML 交付稿。

## Guardrails

- 不把推断写成已确认事实。
- 不一次抛出多个问题，不询问可以从代码或配置确认的内容。
- 不为了完整性扩大范围；大问题先列为非目标或后续项。
- 不在只读意图下写文件。
- 不把 spec 当实施 TODO；复杂实施另交给 `task-todolist-execution`。
- 不创建 ADR，除非决策难回退、存在真实取舍且缺少上下文会造成误解。

## 交接

- 既有代码事实文档：`code-evidence-docs`
- 正式 HTML 外壳：`formal-html-docs`
- 兼容性敏感实施：`safe-editing`
- 行为测试：`test-first-development`
- 生产事件：`production-incident-hotfix`
- 发布范围：`project-release-scope-check`
