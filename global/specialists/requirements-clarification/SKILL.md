# Requirements Clarification

## 目标

通过逐题访谈把模糊想法收敛为可决策、可验收、可交接的需求说明。完成条件是关键设计分支已经确认或明确标为待决策，不是文档足够长，也不是已经进入实现。

## 工作流

1. 确认本次产物是口头梳理、需求草案、方案决策还是正式 PRD/spec。
2. 先读取用户提供的材料和仓库内相关 README、AGENTS、文档、接口、测试与配置；可以查证的事实不要反问。
3. 区分用户观察到的问题与已经提出的解决方案；方案前提未经验证时明确质疑“是否需要这样解决”，不要默认功能请求就是正确问题定义。
4. 找到最小有价值切片：必须端到端产生可验证价值，不能靠省略错误处理、兼容、安全或测试伪造小范围。
5. 建立需求决策树，按实际问题覆盖：目标用户、目标与非目标、核心场景、范围、关键状态、接口/数据影响、约束、失败行为和验收标准。
6. 每次只询问一个会改变方案或验收口径的关键问题；同时给出推荐答案、理由及选择其他答案的影响。根据回答继续追问尚未闭合的分支。
7. 维护简洁决策记录：`已确认`、`推断`、`待确认`、`未验证`。不要把推荐方案自动升级为已确认结论。
8. 存在实质不同的路径时给 2–3 个方案，只比较会影响决策的成本、风险、验证和回退难度。
9. 关键分支闭合后输出需求说明；用户要求正式确认时，先呈现草案并等待确认，再把它视为实施契约。
10. 明确进入实现的前置条件、仍未解决的问题和建议的下一步。

## Spec 最低内容

- 背景、目标和非目标
- 用户与核心场景
- 已确认事实、假设和待决策项
- 推荐方案及必要取舍
- 范围、关键流程与状态
- 接口、数据和依赖影响
- 验收标准与验证方式
- 未覆盖风险和实施前置条件

按问题裁剪章节，不为填满模板制造内容。README、AGENTS、轻量说明默认使用 Markdown；只有用户明确要求自包含正式 HTML 时才配合 `formal-html-docs`。

## 边界

- 不因普通任务存在一个可合理假设的小歧义就启动完整访谈。
- 不询问能从现有材料、代码或配置确认的事实。
- 不一次抛出问题清单；沿当前最关键的设计分支逐题收敛。
- 不在用户要求只讨论或只出 spec 时进入实现。
- 不把 spec 当实施计划；实施步骤和状态交回 Codex 原生计划能力。
- 不自动创建 ADR；只有决策难回退且缺少上下文会造成持续误解时才建议记录。
- 业务术语、身份、状态和 bounded context 的语义歧义使用 `domain-modeling`；不要在本 skill 中展开完整领域模型。
