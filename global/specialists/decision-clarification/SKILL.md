# Decision Clarification

## 目标与模式

用同一套决策树访谈引擎处理三种任务。意图明确时直接选择模式，不额外反问：

- **压力测试**：用户要求 grill、挑战假设、发现盲点或检查计划；目标是在约定范围内暴露重要隐含决策，不默认生成需求文档。
- **需求收敛**：用户要求梳理需求、比较方案、定义成功或形成 PRD/spec；目标是得到可决策、可验收、可交接的需求契约。
- **混合模式**：用户明确要求先挑战想法再形成需求；先完成压力测试，再复用已确认结论收敛需求，避免重复访谈。

## 共同流程

1. 确认访谈范围、所选模式和期望产物；只有模式会实质改变结果且无法从用户表述判断时才询问。
2. 先读取用户材料和当前可访问的文档、代码、配置、测试或可信外部资料。可以查证的事实不要反问；缺少来源时说明缺口并请求材料，不把事实判断伪装成用户选择题。
3. 区分观察到的问题、隐含假设和已经提出的解决方案；前提未经验证时质疑是否需要这样解决。
4. 建立带前置依赖的决策树，先识别根决策再展开下游分支。按任务选择节点：目标与非目标、相关人群、核心场景、替代路径、约束、取舍、失败模式、二阶影响和成功标准；需求模式再覆盖范围、关键流程与状态、接口/数据/依赖和验收方式。
5. 每轮计算 `frontier`：只包含前置决策已经闭合、现在可以独立回答且必须由用户判断的问题。如果一个问题的推荐答案或选项会随另一开放问题的答案改变，它就不是当前 frontier。依赖问题留到后续；需要查证的事实不进入 frontier。
6. 压力测试模式默认询问完整 frontier；frontier 过大到会降低回答质量时，按顶层分支拆轮。需求收敛模式默认选择阻塞范围最大、信息增益最高的 1–3 个问题。混合模式在两个阶段分别采用对应批次策略。
7. 编号提出本轮问题，每个编号只承载一个决策，不把后续问题藏在补充说明里；材料或访问请求单独列出。每题给出推荐答案、理由，以及其他选择对价值、范围、风险、验证或回退的影响。
8. 用户回答后更新决策树并重新计算 frontier；不要继续询问已经失效的问题。维护简洁记录：`已确认`、`推断`、`待确认`、`未验证`，推荐答案不能自动升级为已确认。
9. 存在实质不同的路径时给出 2–3 个方案，只比较影响决策的差异。

## 停止条件与产物

### 压力测试

约定范围内的 frontier 为空后，请用户确认已经形成共同理解。输出已确认决策、暴露的假设、主要风险和仍开放的问题；除非用户要求，不生成 PRD/spec，也不进入实施。

### 需求收敛

会改变目标、范围、方案或验收的关键分支已经确认，或明确标为待决策后即可停止；不为穷尽所有可能问题无限延长访谈。根据领域裁剪需求说明，至少覆盖：

- 背景、目标、非目标和相关人群
- 核心场景、已确认事实、假设和待决策项
- 推荐方案、必要取舍、范围和关键流程
- 依赖、失败行为、成功或验收标准及验证方式
- 未覆盖风险和进入执行的前置条件

软件需求按需加入状态、接口、数据、兼容与安全；非软件产品按需加入交付渠道、运营流程、成本、合规和衡量周期。用户要求正式确认时，先呈现草案并等待确认，再把它视为需求契约。

### 混合模式

先让用户确认压力测试阶段已经充分，再把已确认决策作为需求收敛的输入，只追问尚未闭合的需求契约分支，最终输出需求说明。

## 边界

- 不因普通任务存在一个可合理假设的小歧义就启动完整访谈。
- 不把整棵决策树一次抛给用户；只询问当前 frontier。
- 不在用户要求只讨论、压力测试或只出 spec 时进入实施。
- 不把需求说明当实施计划；执行步骤和状态交回 Codex 原生计划能力。
- 不自动创建 ADR；只有决策难回退且缺少上下文会造成持续误解时才建议记录。
- 业务术语、身份、状态和 bounded context 的语义歧义使用 `domain-modeling`；不要在本 skill 中展开完整领域模型。
