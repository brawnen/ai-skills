# Test First Development

## 适用边界

仅在用户明确要求 TDD/test-first 时使用。缺陷回归、复杂规则或公共契约需要测试，不自动意味着需要本 skill。遵循已确认的行为、验收与项目测试约定；局部澄清和外层验证交给宿主。

根因未知时先定位真实缺陷链路，不用猜测的测试锁定未经验证的根因。测试困难时评估公共测试缝，不为完成 TDD 自动展开重构。

## 证据循环

围绕一个可观察行为建立最小切片：

- **RED**：先写独立行为测试，运行并确认因目标行为缺失而失败；语法、环境和 fixture 错误不能作为 RED 证据。直接通过时确认行为是否已有，或修正测试缝。
- **GREEN**：实现当前行为，运行目标测试确认通过。
- **REFACTOR**：必要时清理结构，保持行为不变并运行受影响测试。

重复到用户授权范围完成。没有实际看到正确原因的失败，不能声称完成 TDD。

## 测试判断

- 断言公共行为、业务结果与稳定契约，避免私有方法、内部调用次数和偶然结构。
- 期望值来自需求、独立示例或外部事实，不复制生产算法作为断言。
- 优先真实内部路径，只替代确有必要的系统边界；边界替身应贴近真实契约。
- 原始症状涉及编排或跨组件时，测试必须覆盖对应链路；局部测试通过不能证明业务恢复。
- 不为迎合实现修改正确测试；行为定义或测试错误时修正并说明。

## 既有实现与替代验证

纯重构已有足够测试保护时直接复用；不足时补 characterization test，可从 GREEN 开始，明确它是保护网。不要删除已有实现来制造 test-first 历史。

没有可靠自动化测试缝或运行环境时，采用可重复的替代验证，说明实际证明的范围；不把编译、人工复现或现有测试通过称为完成 TDD。仅在影响验收或留下重要风险时解释限制。

目标循环完成后，宿主按改动风险安排邻近测试、构建、集成或其他必要检查，不在本 skill 重复调度全套验证。
