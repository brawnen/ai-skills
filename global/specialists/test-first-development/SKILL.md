# Test First Development

## 定位

用 TDD 管理可测试行为的内层实现循环，用 Codex harness 管理外层质量验证。TDD 证明目标测试能捕获缺失行为并驱动最小实现；它不替代邻近测试、全量测试、构建、lint、类型检查、E2E、视觉验证或发布检查。

## 前置判断

1. 确认目标行为和验收口径已经足够明确；只存在局部歧义时使用 Codex 原生澄清，正式需求访谈或 spec 收敛才使用 `requirements-clarification`。
2. 根因未知、难以复现、偶发、性能或跨组件故障先使用 `systematic-debugging`；确认根因和真实缺陷链路后再进入本 skill。生产影响仍在扩大时，由它的 Operational Gate 先控制影响。
3. 找到项目现有测试命令和稳定测试缝。优先选择公共 API、HTTP/CLI、service 边界、组件可观察行为或用户路径，不从私有实现倒推测试。
4. 必要时运行最小基线测试，区分既有失败和本次引入的失败。
5. 测试缝明显时直接推进；只有测试缝会改变公共设计、显著增加成本或影响验收边界时才询问用户。

## RED-GREEN-REFACTOR

对每个 vertical slice 重复：

1. **定义行为**：用用户可观察结果描述一个最小行为和失败场景。
2. **RED**：先写一个最小行为测试，再运行目标测试。
3. **验证 RED**：确认测试因目标行为缺失而失败，而不是语法、环境、fixture 或 mock 配置错误。测试直接通过时，修正测试缝或确认该行为已经存在。
4. **GREEN**：只实现让当前测试通过所需的最小生产代码，不提前实现后续 slice。
5. **验证 GREEN**：重新运行目标测试，确认通过；随后运行必要的邻近测试。
6. **REFACTOR**：全绿后再清理重复、命名和局部结构；不在重构阶段加入新行为，每次清理后重新验证。
7. 进入下一个行为，直到已确认范围完成。

## 测试质量

- 测试公共行为和稳定契约，不断言私有方法、内部调用次数或偶然对象形状。
- 让测试名称表达业务能力或失败行为，使测试可以作为可执行规格阅读。
- 期望值来自 spec、已确认示例或独立事实，不在断言中重复生产算法。
- 一次只证明一个核心行为；避免先写完所有测试再批量实现的 horizontal slicing。
- 只 mock 真正的系统边界，例如第三方 API、时间、随机数、网络或必要的数据存储；优先用真实内部代码路径。
- mock 响应贴近真实边界契约，并断言业务结果，不断言 mock 本身。
- 不要求每个函数都有测试；把测试投入放在关键行为、复杂逻辑、公共契约和高风险路径。

## 既有代码与重构

- bugfix：先写能复现缺陷的失败测试，再修复。
- 纯重构：先用 characterization test 固定现有行为。它可以从 GREEN 开始，但必须明确它是保护网，不是假装完成 RED。
- 用户或仓库已经存在先于测试的实现时，不因 TDD 纪律删除它；为本次新行为建立可证明的测试循环，并如实说明哪些代码不是 test-first 产生的。
- 测试困难通常意味着测试缝或设计需要评估，但不要为了写测试自动展开大规模重构。

## 例外与替代验证

以下任务不机械强制 RED-GREEN：探索性 prototype、纯视觉调整、生成代码、简单配置、没有可运行测试环境的遗留代码，以及自动化测试无法安全覆盖的外部系统操作。

使用例外时，在实现前尽可能说明：

- 为什么没有可靠测试缝或不适合 test-first。
- 使用什么替代反馈回路，例如编译、类型检查、现有回归套件、集成/E2E、浏览器视觉检查、最小复现或人工步骤。
- 剩余风险是什么，以及后续能否补回归测试。

## 完成条件

- 没有亲眼看到目标测试因正确原因失败，就不能声称完成了 TDD。
- 不为迎合实现而修改正确的失败测试；需求或测试本身错误时，先修正行为定义并说明原因。
- TDD slice 完成后，继续执行 Codex harness 选择的外层验证；只有实际运行的结果可以作为完成证据。
