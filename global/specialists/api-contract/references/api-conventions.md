# 前后端 HTTP JSON API 默认规范

版本：1.0；整理日期：2026-10-30。

这是从实际前后端契约讨论中提炼的个人项目默认规范。适用于由项目控制的普通业务 HTTP JSON 接口；文件下载、流式响应、第三方回调按各自协议。它不指定语言、框架、认证产品或部署形态，也不是唯一行业最佳实践。

API指应用程序接口；JSON是结构化数据交换格式；OpenAPI是机器可读的HTTP接口描述；DTO指接口传输数据结构；CI指持续集成。下文用这些术语区分结构约定、业务规则与运行验证。

## 1 采用与项目差异

新项目直接采用以下默认值，不重复逐项确认。已有契约或本次明确决定优先；旧系统的改变按兼容迁移处理，不能把个人偏好当作现有客户端已支持的事实。

| 项目参数 | 无其他约定时的默认值 | 需要适配的情况 |
| --- | --- | --- |
| 业务响应策略 | 成功及预期业务拒绝均为HTTP 200，靠code区分 | 现有接口已按HTTP状态表达业务拒绝；保留或明确设计迁移 |
| 响应结构及成功码 | code、message、data、request_id；成功码为字符串OK | 已有兼容要求；成功码集合必须显式声明 |
| 金额 | 最小货币单位的整数字符串；人民币示例为分 | 非人民币、多币种或不同金额精度；明确币种和单位 |
| 百分比例 | 百分数定点字符串，默认两位小数 | 业务要求更高精度；支付手续费率单独确定，不套用分润精度 |
| 业务时区 | Asia/Shanghai；时点响应使用+08:00 | 跨国、多时区或已有业务日历；按项目明确，不能依赖主机默认值 |
| 普通管理列表 | page、page_size；page从1开始 | 连续流水、流式读取、大数据遍历等另按场景选分页方式 |
| 新接口版本路径 | /api/v1/ | 已有路由、第三方协议、网关或客户端兼容要求 |

比例两位小数、人民币分、北京时间和页码分页都是可覆盖的默认值。页大小默认／上限、金额正负及范围、具体错误码、认证／CSRF（跨站请求伪造）机制、幂等依据由项目确定，不预设数值。

## 2 普通JSON响应

应用可控的普通JSON响应使用`application/json`，固定四个顶层字段：

| 字段 | 类型与含义 |
| --- | --- |
| code | 字符串；OK表示请求成功处理，其他稳定语义码表示业务拒绝或公共错误，不靠中文提示或HTTP数字推断所有原因 |
| message | 始终为对象；title、detail固定为字符串，无补充说明时detail为空字符串；可选字段错误信息的结构由项目统一声明 |
| data | 所有业务结果放在此字段；无结果或业务拒绝默认null，具体对象／集合按接口定义 |
| request_id | 受控字符串；关联本次应用响应、日志和适用的审计记录 |

成功示例，仅说明格式：

```json
{
  "code": "OK",
  "message": {"title": "请求成功", "detail": ""},
  "data": {"id": "1234567890123456789", "amount_fen": "12345"},
  "request_id": "req_example"
}
```

预期业务拒绝示例，HTTP仍为200：

```json
{
  "code": "VERSION_CONFLICT",
  "message": {"title": "数据已更新", "detail": "请刷新后重新确认本次修改。"},
  "data": null,
  "request_id": "req_example_conflict"
}
```

错误码稳定，提示可调整；前端不解析中文决定业务分支。未知或新增code不得当作成功，只有显式成功码才进入成功分支。提示不包含SQL、堆栈、凭据或无权对象信息。

查询成功可以返回失败任务；异步受理成功可以返回待处理状态；导入成功受理可以包含逐行失败。这些状态归data，不能用HTTP200或OK宣称任务已完成、整批成功或业务资料完整。被拒操作不产生被拒业务写入，必要安全审计另行处理。

## 3 错误分类与前端处理

| 分类 | 默认表达 | 前端责任 |
| --- | --- | --- |
| 业务成功、查询成功、异步受理 | HTTP200＋OK；data包含结果或当前状态 | 业务分支读取结果，分别判断任务／逐项状态 |
| 合法请求违反业务约束 | HTTP200＋非成功业务码；如版本冲突、业务比例或有效期不合法 | 业务分支按code处理并展示message，原业务状态保持 |
| 未认证、无功能权限、资源不存在／不可见 | HTTP401、403、404；不可见资源按项目避免暴露存在性 | 公共请求层处理认证／访问；应用可控JSON仍为四字段 |
| 请求无法解析或协议不满足 | HTTP400；按情况405、413、415等 | 公共请求层处理协议错误 |
| 限流、应用或依赖故障 | HTTP429、500、503等 | 公共请求层展示安全提示，重试按场景决定 |
| 代理HTTP错误、非JSON或其他不符合契约响应 | 保留真实HTTP状态及可用请求标识 | 公共请求层兜底，不展示原始错误页 |
| 无可读响应／成功状态但格式不符 | 无响应没有真实HTTP状态；成功响应格式不符为契约异常 | 生成本地提示，不伪造服务端状态或request_id |

公共请求层先判断响应是否可读及真实HTTP状态；HTTP200且结构合法后，再按code进入业务分支。非200可尝试读取规范message及request_id，失败时用本地提示。取消、超时、其他无响应可在客户端区分，但无法确定的原因不猜测。

业务必填／比例／有效期等可正常判定的校验与协议错误分开；例如可解析对象缺少业务必要内容可以是业务拒绝，破损JSON或不可接受类型属于协议错误。逐接口说明，并检查框架／OpenAPI自动校验是否提前改写了状态码；可缺省字段与业务上必填不是同一层概念。

HTTP成功率与业务成功率分别统计；业务拒绝虽为HTTP200，仍按code计量。此分层是本规范的项目选择；[HTTP语义标准](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)定义状态码，并不规定所有项目必须采用这种业务码方案。

## 4 请求关联与重试

request_id由可信入口产生或验证接续，应用响应与日志保持一致，也可放入响应头；不无条件采信客户端值。代理或早期协议失败可能没有应用标识，客户端诊断引用须与服务端request_id分开。

重试是新请求，可以有新request_id；业务ID、任务ID和幂等标识分别承担其职责。超时或断网不证明服务端没有执行；写操作按该场景的防重、查询结果和恢复约定决定是否重试，不统一盲目重发。

## 5 数据表示

| 类别 | 默认传输表示 | 约束 |
| --- | --- | --- |
| ID／业务编号 | 字符串 | 前端按标识处理，保留外部编号前导零；不反推内部主键类型或生成算法 |
| 金额 | 最小单位的整数字符串，如amount_fen为字符串12345表示人民币123.45元 | 内部精确计算，不能先经浮点近似再转字符串；正负、范围、币种及舍入按业务定义 |
| 百分比例 | 定点字符串，如share_percent为字符串5.00表示5% | 显式精度及单位；分润比例和支付费率分开定义 |
| 具体时点 | 带时区RFC3339字符串，如2026-10-30T10:30:00+08:00 | 按实际时点解释，保留所需源精度；业务日／月按明确业务时区归属 |
| 业务日期／月份 | YYYY-MM-DD／YYYY-MM字符串 | 表示业务日历，不能按UTC转换偏移成另一日或月 |
| 未知值 | null，配对象级缺项信息说明原因 | 不用0、空字符串或默认身份补造未知事实 |
| 真实零值 | 遵守字段类型；零金额为字符串0 | 与未知、字段缺省分开 |
| 普通计数／分页参数 | JSON整数 | 接口声明范围；超出客户端安全整数能力时另定义表示 |

JSON示例中的`"amount_fen":"12345"`和`"share_percent":"5.00"`都是真正字符串。字段命名沿用项目已有风格，必须清楚表示单位；不强制把现有camelCase改成示例的snake_case。

前端统一做精确输入转换和展示，后端执行最终业务校验／核算。传输字符串不改变业务比例、舍入和数据库类型。具体时点格式依据[RFC3339](https://www.rfc-editor.org/rfc/rfc3339.html#section-5.6)；采用字符串避免长标识和金额发生数值近似，是项目选择，JSON数字互操作边界见[RFC8259](https://www.rfc-editor.org/rfc/rfc8259.html#section-6)。

## 6 普通列表分页

请求使用page、page_size；响应在data内包含items、page、page_size和total。示例中的20仅为演示，不是默认页大小：

```json
{
  "code": "OK",
  "message": {"title": "请求成功", "detail": ""},
  "data": {"items": [], "page": 1, "page_size": 20, "total": 0},
  "request_id": "req_example_list"
}
```

先应用授权和筛选，再统计和分页；total只反映该范围的可查记录数，不能泄露其他组织数量，也不证明外部来源完整或已对账。items空时为[]；当前页为空不必然意味着total=0。

后端提供稳定排序，同值追加唯一排序依据。固定数据集跨页可预测；实时翻页仍可能因新增／更新变化，不能承诺冻结快照。冻结账单按冻结版本查询；需要连续遍历的流水另设计游标等方式，不将该需求强塞进普通页码分页。

## 7 契约维护与类型生成

OpenAPI维护路径、参数、认证要求、字段类型、必填／可缺省、null、响应及示例；业务政策、权限范围和异常处理仍维护于项目规格，两者引用而非复制一整套规则。规范能力见[OpenAPI官方说明](https://spec.openapis.org/oas/v3.1.2.html)；该链接是参考，不指定项目必须使用3.1.2。

契约先形成，再同步前后端。Go／Java／其他后端的接口传输类型及前端类型按项目工具从契约生成，生成文件不手工修改。领域模型、数据库结构和接口类型分别转换，不能因工具方便就让数据库生成结构直接成为外部契约。

单门户保留单入口；多门户按各自可访问能力分别描述，共享必要的公共定义。服务地址与路径组合对应客户端可见URL，内部代理前缀单独维护。认证拓扑、Cookie／令牌、代理和供应商协议依项目决定，不从本规范附带引入。

绑定当前可用的OpenAPI格式版本、生成器、校验器、配置及精确版本；工具能力需按实际版本核对，不默认安装某个库。HTTP200响应须覆盖成功及业务拒绝，公共错误逐状态描述；生成客户端不能把每个200都视为业务成功。

## 8 版本与兼容升级

新接口默认/api/v1/；接口主版本、OpenAPI格式版本及应用发布版本分别管理，日常发布不自动增加URL版本。

| 变化 | 处理 |
| --- | --- |
| 新增接口、可选输入、允许旧客户端忽略的响应字段 | 核对旧客户端／请求仍可使用后，作为同主版本兼容新增 |
| 删除／改名字段，改变类型、单位、字段或业务码含义，可选输入改必填 | 设计兼容过渡；无法保持旧契约时使用新主版本 |
| 新增枚举值 | 单独评估旧客户端的穷举及未知值分支，不默认算兼容 |

默认后端先提供兼容能力，再更新前端，最后在约定退出条件满足后清理旧能力；考虑未刷新的浏览器及尚未升级的客户端。不得仅因新前端发布就删除旧能力，也不要求新项目立刻实现v2。数据库结构、任务消息及其他消费者的兼容另行处理。

## 9 按产物验证

- 只有规范：检查链接、表格、JSON示例及规则一致性；标明未运行真实接口。
- 已有OpenAPI：使用绑定工具解析、校验、生成；CI检查生成可重复和差异，核对可缺省／null、金额字符串及业务拒绝映射。
- 已有实现：真实入口验证成功、业务拒绝、认证／权限拒绝、代理异常与无响应兜底；核对持久化副作用和请求关联。生成类型不是运行时验证。
- 有兼容升级：保留实际前后端版本、契约差异及旧请求／旧客户端运行证据；语义兼容仍需人工业务判断，不能只靠自动差异工具或编译判断。
