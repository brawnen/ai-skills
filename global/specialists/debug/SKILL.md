# Systematic Debugging

## 生产影响仍在扩大时

先保存足以支持诊断的错误、时间线和关键观测，再优先控制影响。选择适用的可逆止损措施，明确影响面、验证信号和撤销条件；复用已有授权，不因本 skill 扩大生产操作权限。

用用户影响或业务指标确认止损效果，命令成功不等于恢复。临时措施应保留撤销条件，服务恢复不等于根因解决；必要止损不等待完整根因分析。

## 真实症状与反馈

建立能捕获用户原始症状的反馈：失败测试、请求或事件重放、版本对照、压力循环、定向观测或结构化人工步骤。选择最能区分原因的方式，不遍历工具清单。

- 确定性故障检查重复性；偶发故障记录复现率、时间窗口和条件，修复后的短暂未出现不能证明消除。
- 缩小输入、依赖或步骤时保留同一症状，避免把环境错误当成最小复现。
- 无法重放时可继续用日志、trace、现场状态和配置差分缩小范围；说明证据限制，仅请求会改变诊断的缺失信息，不把单一候选写成已确认根因。

## 可证伪假设

根据证据提出候选原因及区分它们的预测：如果 X 是原因，改变或观测 Y 应产生 Z。证据已唯一指向原因时无需凑齐多个假设。

- 每次探测控制变量，优先能排除候选的检查；失败后更新假设，不在旧修复上叠加猜测。
- 跨组件故障定位输入、输出、状态或配置第一次偏离的位置，核对实际路由与运行环境。
- 性能故障先确定负载和基线，再使用 profiler、计划或测量比较；不凭体感判断。
- 近期变更与故障相关不等于因果。多个不同修复仍无效、证据互相矛盾或复现条件变化时，重新检查反馈、测试缝和架构假设；只有需要用户决策时才提问，不按失败次数强制停工。

## 根因与修复证据

用针对性干预或独立边界证据验证因果关系。采用针对根因的修复，避免混入无关重构。

有可靠测试缝时增加或复用能捕获真实缺陷链路的回归测试；用户明确要求 TDD 时才加载 `tdd`。无法自动化时使用原始反馈或适用替代验证，不制造无法捕获真实问题的浅层测试。

复跑原始症状反馈，宿主按风险安排必要外层检查。涉及数据库实际变更且存在专项风险时使用 `review-db`，不因为排障涉及数据库就自动加载。

收尾清理临时探针，确认止损已撤销或说明保留原因和撤销条件。交付根因、关键证据、实际修复、验证范围和剩余未知；临时恢复、重试或屏蔽错误不能作为永久修复证明。日志和样本保持脱敏。
