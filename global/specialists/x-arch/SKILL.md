# 架构摩擦体检

## Goal

只读发现架构摩擦，输出有证据的改进候选。吸收 `improve-codebase-architecture` 的模块深化、deletion test、局部性与变更热点优先（YAGNI）思路，保持默认只读、候选化、证据分层。模块与边界判断原则见 [架构参考](references/architecture-design.md)。

## Vocabulary

使用统一词汇表达架构判断，避免泛泛说“代码不优雅”：

- **模块**：有接口和实现的代码单元，可以是函数、类、包或业务切片。
- **接口**：调用方必须知道的一切，包括签名、参数、顺序、错误模式、配置和性能特征。
- **实现**：模块内部代码。
- **深度**：接口提供的杠杆。深模块是小接口承载较多行为；浅模块是接口复杂度接近实现复杂度。
- **缝**：可以替换行为而不原地改代码的位置。
- **适配器**：填入某个缝的具体实现。
- **杠杆**：调用方用较少接口知识获得较多能力。
- **局部性**：变化、缺陷和验证是否集中在一个地方。

## Default Mode

- 默认只读：不改代码、不写 repo 文件、不默认生成报告文件、不打开浏览器。
- 默认输出候选清单和证据分层。
- 用户明确要求正式 HTML 架构报告时，配合 `x-html` 生成自包含 HTML。
- 用户选中某个候选继续设计或实现时，衔接 `x-spec` 或交回宿主原生工作流。

## Workflow

1. **收敛扫描焦点（YAGNI）**：
   - 用户已指定模块、业务链路或痛点时，直接锁定该范围。
   - 用户要求扫描整个仓库时，先查看近期 `git log` 高频变更热点（hot spots），优先聚焦反复修改、缺陷集中的路径；极少变动的稳定冷代码即使偏浅，深化收益也低，不列为高优重构对象。
2. **读取项目事实与历史决策**：读取 README、AGENTS、`GLOSSARY.md`/`CONTEXT.md`、既有 ADR、测试目录与相关源码。
3. **核对调用链与摩擦信号**：
   - 理解一个概念需要在许多小文件之间来回跳转（单调用方透传过多）。
   - 模块只是透传，接口几乎和实现一样复杂。
   - 逻辑为了单测被拆成碎函数，但真实 bug 出现在编排调用处；或内部调用链层层重复做本应在外部边界一次完成的防御校验。
   - 调用方必须知道太多顺序、配置、错误模式或隐含状态约定。
   - 多处调用方重复同一段校验、补偿、转换、异常处理，或多次 AI 迭代在不同模块复制出近义 helper / DTO 转换胶水代码（Deslop 候选）而未收敛回公共层。
   - 外部依赖、第三方接口或跨服务调用没有清晰缝和适配器。
4. **执行 deletion test**：如果删除该模块，复杂度是直接消失（说明是无价值透传），还是散落到 N 个调用方（说明有封装价值）？
5. **依赖分类与测试缝映射**：进程内纯逻辑 / 本地可替代（DB、文件系统） / 远程自有服务 / 第三方外部依赖。
6. **核对既有 ADR 冲突**：若某个改进候选与既有 ADR 明确冲突，仅当现实摩擦已足以支撑重审该决策时才保留，并在候选中显式标注“与某 ADR 冲突及值得重开的依据”；不重提已被合理否决的理论重构。
7. **排序推荐与下一步**：按 `Strong / Worth exploring / Speculative` 排序，给出唯一 Top Recommendation 与最优下一步（写 `x-spec`、补测试缝、局部实现或暂不动）。

## Guardrails

- 不把“看起来不优雅”或冷代码静态形态当作高优重构理由。
- 不默认写代码、创建 HTML 或修改词汇表/ADR。
- 不输出没有具体文件、调用链或测试证据的空泛观点。
- 用真实变化、外部依赖隔离和测试收益判断抽象缝；不为假想扩展增加包装层。

## Coordination

- 需要输出正式可打印 HTML 架构报告：配合 `x-html`。
- 选中候选进入技术规格设计：使用 `x-spec`。
- 来源于生产故障：先用 `x-debug` 止损并验证根因，再评估架构候选。
- 业务术语或上下文状态边界混乱：使用 `x-req` 对齐领域语言；跨服务/部署边界风险按需读取 [跨边界设计参考](references/cross-boundary-design.md)。
