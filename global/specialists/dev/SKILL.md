# 研发交付

入口负责团队交接契约，规划、实现、测试和状态维护由宿主执行。只组合当前需要的部分；不为阶段切换重复访谈、生成文档或审批。

## 选择路径

先复用目标、非目标、必须保留的行为、验收来源、项目事实与授权。风险取决于后果、影响面、可逆性和验证难度，不按任务大小或会话数自动判定。

- 小且明确：宿主直接实施、运行相关检查，给出简短证据。
- 需交接的新行为：必要时用 `to-spec` 补技术与验收契约，再按完整行为切片实施。
- 权限、资金、数据、跨部署兼容或恢复风险：补相关专项与独立证据；有价值且获授权时再增加交叉审查。

关键需求不明确时选择 `to-decision`；身份/状态语义影响设计时用 `model`；跨部署契约风险用 `review-cross-stack-change`；数据库实际变更用 `review-db`。没有对应缺口就不加载。不自动启用 TDD、多代理或完整 UI 流程。

## 阶段交接

需求与必要架构 → 技术/验收契约 → 行为切片与依赖 → 宿主实现/快速反馈 → 必要变更验证 → PR/CI → 人合并 → 测试环境自动部署及 smoke → 人工生产发布包。

`verify-change` 用于需要验收映射与证据判断的变更；项目缺少可用运行入口时，按需用 `setup-verification` 建立它。能力不可用时继续可完成部分，准确标出缺口，不把编译通过或报告写完当完整交付。

需要交接格式或发布判定时读取 [产物契约](references/artifacts.md) 的对应部分；小任务不填完整模板。预期来自已确认业务标准，不能从当前实现反推。可实验查证的事实先查证，未确定的业务目标仍需人决定。

## 上下文与边界

连贯上下文仍有效时继续；自包含任务、换人/换 Agent、独立并行或上下文拥挤时再切换。携带 spec/任务、必要原始材料、目标版本、已确认决定和剩余问题，不强制每个切片新开任务。

已有验收和授权复用；新增核心业务取舍或难回退方向才确认。代码合并、生产部署、回滚和生产数据写入由人执行。Agent 准备发布包，并在允许范围内报告只读生产 smoke；测试环境自动化也遵循项目既定权限。

失败先保存证据并分类。可修复则继续；无新证据的重复失败检查假设和反馈循环。环境、权限或业务决定阻塞时只停依赖部分。生产影响扩大先保存观测并在允许范围内控制影响，恢复不等于根因解决。
