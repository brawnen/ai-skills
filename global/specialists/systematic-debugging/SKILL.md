# Systematic Debugging

## 目标

用可重复证据替代猜测：先构造能捕获用户真实症状的反馈循环，再缩小问题、验证根因、建立回归测试并实施单一修复。生产影响仍在扩大时，先控制影响，再继续根因诊断。

## Operational Gate

开始诊断前先判断：生产用户、资金、数据、安全或关键业务是否仍在受影响或继续扩大。

如果否，直接进入“反馈循环”。如果是：

1. 保存原始症状、错误、时间线、日志、trace 和关键指标，避免止损动作抹掉证据。
2. 确认影响范围、扩大速度和当前可观察的成功/失败指标。
3. 提出可逆止损选项，例如限流、隔离、降级、暂停入口、回滚或关闭开关；说明绕过面、误伤面、撤销条件和验证方式。
4. 生产操作必须获得用户授权并遵守宿主权限边界；不要因为命中本 skill 自动扩大操作权限。
5. 执行获批措施后，用用户影响和生产指标确认影响停止或显著下降；命令成功不等于止损成功。
6. 把止损标记为临时措施，保留负责人、期限或撤销条件，然后进入正常诊断。

不要用完整根因分析拖延必要止损，也不要把恢复服务等同于根因已经解决。

## 反馈循环

优先建立一个能够因当前缺陷变红、修复后变绿的命令或可重复步骤：

1. 单元、集成、契约或 E2E 失败测试。
2. curl/HTTP 请求或消息 payload replay。
3. CLI + fixture + 期望输出 diff。
4. 浏览器自动化，断言 UI、console 或 network 行为。
5. 捕获并重放 trace、HAR、事件或生产样本的脱敏副本。
6. 只启动必要组件的 throwaway harness。
7. property/fuzz/stress 循环，提高偶发问题的复现率。
8. `git bisect run`、旧新版本对照或配置差分。
9. 无法自动化时，使用结构化人工步骤记录输入、时间点和观察结果。

反馈循环应尽可能满足：

- **对症**：捕获用户描述的同一个问题，而不是附近的另一个失败。
- **可重复**：确定性问题稳定复现；偶发问题达到足够高且可测量的复现率。
- **快速**：优先秒级，隔离无关初始化和依赖。
- **可运行**：Agent 可以重复执行；人工步骤必须结构化。

如果无法建立反馈循环，列出已尝试的方法并请求缺失的日志、HAR、core dump、录屏、环境访问或临时观测授权。没有反馈循环时不要直接输出单一根因结论。

## 复现与最小化

1. 运行反馈循环，保存原始失败证据并脱敏敏感信息。
2. 一次删除一个输入、调用方、配置、数据或步骤，每次重新运行。
3. 保留仍能触发同一症状的最小场景；不能再删除任何要素时停止。
4. 检查近期 diff、依赖、配置和环境差异，但不要把相关性自动当成根因。

## 假设与探测

1. 基于最小复现列出 2–5 个按证据排序的假设；证据已唯一指向一个原因时，说明为何无需扩展假设集。
2. 为每个假设写出可证伪预测：如果原因是 X，那么改变或观测 Y 应出现 Z。
3. 优先使用 debugger、REPL、profiler、query plan 或边界处的定向日志；不要先“全量打日志再 grep”。
4. 一次只改变一个变量，并让每个探针区分至少两个候选假设。
5. 跨组件链路在每个边界验证输入、输出、状态和配置传播，定位第一个偏离点。
6. 临时日志使用唯一前缀并避免输出凭据、token、认证头或个人数据。
7. 性能问题先建立基线和 profiler/query plan，再比较和二分；不要用主观体感代替测量。

假设失败后回到证据，不要在旧修复上继续叠加猜测。连续三次修复尝试失败，暂停并评估测试缝、共享状态、耦合或基础架构假设是否错误，再与用户讨论是否需要架构调整。

## 修复与回归

1. 根因确认后，在能覆盖真实缺陷链路的稳定公共缝建立回归测试；使用 `test-first-development` 执行 RED-GREEN-REFACTOR。
2. 没有正确测试缝时如实记录，这是架构发现；不要写一个无法捕获真实问题的浅层测试制造安全感。
3. 只实施针对已确认根因的最小修复，不混入无关重构或顺手清理。
4. 先运行回归测试，再复跑原始未最小化反馈循环，最后执行 Codex harness 选择的邻近和外层验证。
5. 涉及 DDL、迁移、回填或生产数据写入时同时使用 `db-change-safety`。

## 收尾

- 清理带唯一前缀的 debug 日志、探针和 throwaway harness；无法清理时登记位置和后续动作。
- 确认临时止损措施已撤销，或明确保留原因、风险和撤销条件。
- 汇总根因、关键证据、实际修复、回归证明、原始反馈循环结果和剩余未知项。
- 架构问题只作为后续候选；需要正式只读体检时再使用 `architecture-friction-scan`。

## Guardrails

- 不根据接口名、相邻代码或单条日志直接认定根因。
- 不在未复现目标症状时修改多个变量碰运气。
- 不把 warning-free、进程未崩溃或页面提示成功当作业务成功。
- 不为迎合实现修改正确的失败信号。
- 不在输出中泄露秘密或未经脱敏的生产数据。
- 不把临时恢复、重试或屏蔽错误包装成永久修复。
