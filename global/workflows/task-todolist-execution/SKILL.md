# Task Todolist Execution

## 角色边界

只管理“下一步做什么、当前状态、验证门槛和何时交接”，不复制专项规则：

- 需求未确认：`requirements-clarification`
- 兼容性和改动范围：`safe-editing`
- 行为测试：`test-first-development`
- 数据库风险：`db-change-safety`
- 上线决策：`project-release-scope-check`

## 何时使用

满足以下任一条件，并且确实需要持续维护顺序、依赖或验证状态时触发：

- 后续步骤依赖前一步产物或决策
- 跨模块、跨系统或跨角色交接
- 高风险任务包含预检、实施、验证、回滚等阶段
- 任务持续较久，需要中断后恢复状态
- 用户明确要求按 TODO 执行或落盘任务清单

不要用于单次局部修改、同一机械修改、纯问答、只读分析、内容写作、链接或格式修正。文件多不等于流程复杂。

## 执行规则

1. 目标不清时先交给 `requirements-clarification`，不要用 TODO 掩盖需求不确定。
2. 开始有副作用的操作前建立计划；优先使用宿主原生任务工具。
3. 每个步骤包含动作、涉及范围和验证方式；只有中大型任务需要落盘表格。
4. 同一时间只保留一个核心步骤为执行中；真实并行任务明确标注并行。
5. 完成一步立即更新状态。未验证的步骤不能标记为完成。
6. 阻塞时记录原因、影响范围和可选下一步；调整计划时说明原因。
7. 只在需要时加载专项 skill，不因任务复杂就叠加所有能力。

## 状态表达

优先使用宿主支持的 `pending`、`in_progress`、`completed`。待验证、阻塞或跳过没有原生状态时，在步骤文本前加 `[待验证]`、`[阻塞: 原因]` 或 `[跳过]`，不要伪装成完成。

## 是否落盘

- 默认使用宿主原生计划，不创建额外文件。
- 需要跨会话、跨角色交接或用户明确要求时，遵循项目现有 TODO/docs 约定。
- 项目无约定时，使用 `.tasks/<topic>.md` 或与正式设计文档同目录的 `*-todolist.md`。
- 同一任务只维护一个事实源，避免对话计划与落盘 TODO 长期分叉。

落盘内容只需包含：目标、范围/非范围、风险，以及带状态、步骤、涉及范围和验证方式的 TODO 表格。

## 收尾

按任务复杂度简洁说明实际改动、验证结果、未验证项、阻塞和遗留风险。发布判断必须另交给 `project-release-scope-check`，不能由“任务完成”推导。
