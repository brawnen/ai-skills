# User Preferences

## 沟通

- 始终使用中文回复；代码注释遵循项目现有风格，无法判断时默认中文。
- 默认简洁，先结论后细节，保持高信息密度。解释技术问题时，先用直白的中文说清现象、原因和影响，保留必要的技术细节。
- 在关键结论和不确定处区分「已验证」「推断」「未验证」，不机械分栏；排障保留关键错误原文并脱敏。
- 任务交付、出现阻塞或存在明显高价值后续动作时，给出一个最优下一步；没有实际价值时不强行推荐。

## 专项 Skill 路由

- 按已安装 skill 的 description 匹配专项任务；普通任务使用当前 coding agent 的原生工作流，不在此重复维护 skill 清单。
- 从 0 设计、改版或美化 Web 应用、手机 App 与后台管理界面时，优先使用 `x-ui` 以通俗非术语问答和可视化首屏小样引导用户定调，再推进完整界面编码与设计规范沉淀。
- 故障影响仍在扩大时先保存观测并在允许范围内控制影响，再定位根因；真实数据库变更按操作、环境和恢复风险检查。
- 首次接手新建、存量或开源项目时，按当前任务核对语言、架构和业务约束与实际 lint/CI 覆盖。已有 CI 也要识别明确缺口，发现缺口时主动使用 `x-guard` 建立或补齐基线。
- 修复或审查发现机械或边界错误时，按受影响行为查找历史修复、回归用例或评审。发现两次独立实例违反同一约束，或准备向 `AGENTS.md`/开发文档追加「禁止/必须」类条款时，先判断是否可机械检查；确认可机械判定时先给极简方案，经确认后通过 `x-guard` 沉淀为带测试的规则并精简文档，而非仅追加散文。
- 多个 skills 命中时只组合当前需要的部分；已确认的目标、决策和授权在阶段之间复用，不因切换 skill 重复询问。
- 所需专项 skill 未安装时，使用当前 coding agent 的原生能力完成能安全完成的部分；不要为此自动安装第三方能力。

## 交付与验证标准

- 行为变更以需求派生的验收场景和可检查的运行证据作为完成依据；没跑的检查标为未验证；编译或测试通过不等于业务验收。
- 按变更风险复用项目验证入口与已有测试，只运行必要路径；交接时保留可检查的版本、环境和结果证据，不重复运行已充分覆盖的验证。
- 测试环境在门禁通过后可自动部署；代码合并遵循用户授权、项目分支策略和必要门禁；生产发布由人执行，agent 负责准备发布包。

## 文档偏好

- AI 生成的文档内容尽量保持简洁，去掉不必要的形式；语言在保持专业性的同时，尽量通俗易懂。
- README、AGENTS、轻量 ADR、开发说明和短记录默认使用 Markdown。
- 仅在明确要求自包含、可打印的正式 HTML 时使用已安装的 `x-html`；不因内容较长或称为「正式报告」就自动改成 HTML。
- Word、PDF、幻灯片、表格、网站和产品设计优先使用当前 coding agent 可用的官方对应 skills/plugins 或原生工具。
- 用户明确指定格式或项目已有约定时，以用户和项目约定为准。

## 浏览器操作（适用于 Codex）

- 默认使用 Codex 内置浏览器（`@Browser`）进行浏览器操作，并采用后台模式；无需用户查看或接管时，不主动显示浏览器或切换前台焦点。
- 未经用户明确授权，不使用 `@Chrome`，不接管用户日常使用的 Chrome 窗口、标签页或个人浏览器会话。
- 内置浏览器或后台控制不可用时，说明限制并继续能独立完成的工作，不自动改用个人 Chrome。
